# Задание 10 — Обнаружение и диагностика тупиков (Deadlock)

**Проект:** `Lab5/Task10` · **Запуск:** `cd Lab5/Task10 && dotnet run` (безопасный режим) или `dotnet run -- deadlock` (реальное зависание)
**Источник:** `ЛАБ_5Многопоточ.docx`, раздел «Обнаружение и диагностика тупиков Deadlock»

## Что делает программа

Два режима работы:

* **по умолчанию** — инструментированная версия: та же взаимоблокировка
  моделируется, но с таймаутом, поэтому программа **всегда завершается** и её
  можно безопасно показывать преподавателю;
* **`-- deadlock`** — настоящий дедлок: программа зависает намертво (для
  демонстрации в Visual Studio).

### Часть 10.1. Искусственный deadlock

Два объекта блокировки `_lockA` и `_lockB`. Поток 1 берёт A, затем ждёт B;
поток 2 берёт B, затем ждёт A. Классический цикл ожидания.

```
--- Режим: deadlock (зависание намеренное) ---
Поток 1: захватил A, ждёт B
Поток 2: захватил B, ждёт A
```

### Часть 10.2. ASCII-аналог Parallel Stacks и граф ожидания

В режиме по умолчанию печатается граф «кто какой ресурс держит и какого ждёт»:

```
Thread1 -> lockA -> ждёт lockB (держит Thread2)
Thread2 -> lockB -> ждёт lockA (держит Thread1)
Вывод: обнаружен цикл ожидания, это взаимоблокировка (deadlock).
```

Это содержательный аналог окна **Parallel Stacks** в Visual Studio: строки
потоков стеком друг над другом, и видно, на какой строке стоит каждый.

### Часть 10.3. Как избежать: единый порядок блокировок

Оба потока берут замки строго в порядке A → B. Цикл ожидания становится
невозможен по построению. Программа показывает, что оба потока завершаются
и взаимоблокировки не происходит.

Вывод: единый глобальный порядок блокировок — универсальное решение,
не требующее таймаутов.

### Часть 10.4. Как обнаружить: Monitor.TryEnter с таймаутом

Вместо `Monitor.Enter` используется `Monitor.TryEnter(obj, timeout)`. Если
замок не достался за отведённое время, программа сообщает, какой ресурс
занят и кем (берётся `ThreadState`/владелец), и выходит из критической
секции вместо зависания.

```
Monitor.TryEnter(lockB, 500) вернул False — ресурс занят другим потоком.
Вывод: вместо зависания получена диагностическая информация.
```

### Часть 10.5. Диагностика без Visual Studio

Программа печатает информацию, которую обычно дают инструменты отладки:
идентификаторы потоков (`gettid` через P/Invoke `libc`), `ProcessThread`
(идентификатор, состояние `Wait`, `WaitReason`) для каждого потока процесса.
Это показывает, как выглядит дедлок на уровне ОС.

## Ключевые выводы

1. Deadlock — это цикл ожидания, а не просто долгое ожидание.
2. На Windows его видно в Parallel Stacks / Threads / Break All; на Linux —
   `dotnet-stack`, `dotnet-dump` + `clrstack`, `ProcDump`.
3. `Monitor.TryEnter` с таймаутом превращает зависание в диагностируемую ошибку.
4. Единый порядок блокировок надёжнее таймаутов: он устраняет причину.
5. Настоящий дедлок воспроизводится только в режиме `-- deadlock`; в
   безопасном режиме ничего не зависает.
