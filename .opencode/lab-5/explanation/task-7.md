# Задание 7 — Комплексное: параллельная обработка данных

**Проект:** `Lab5/Task7` · **Запуск:** `cd Lab5/Task7 && dotnet run` (по умолчанию 10 млн элементов, можно задать: `dotnet run -- 5000000`)
**Источник:** `МногопотАинхПрогр.docx`, задание 7

## Что делает программа

Комплексный пример: один и тот же массив обрабатывается четырьмя способами,
результаты сравниваются, и делается честный вывод о том, когда параллелизм
оправдан.

Размер массива печатается в заголовке, поэтому преподаватель сразу видит,
какой объём данных обработан.

### Часть 7.1. Синхронный цикл

Базовая линия: последовательный проход, вычисляются сумма, минимум, максимум
и среднее.

### Часть 7.2. Parallel.For с локальными переменными

Используется перегрузка с `localInit` / `localFinally`: каждому потоку
достаётся собственный частичный итог, который затем сводится. В вывод
выводится число блокировок в агрегаторе — оно не превышает числа ядер, а не
числа элементов.

### Часть 7.3. Parallel.ForEach с Partitioner

Массив делится `Partitioner.Create` на 8 частей (по числу ядер) и на 4 части.
Печатается фактическое число обработанных частей — доказательство, что
разбиение отработало.

### Часть 7.4. Тяжёлая операция: честное сравнение

Сложение на элемент слишком дёшево, поэтому параллелизм проигрывает. Тогда
программа повторяет тот же эксперимент с настоящей арифметической нагрузкой
и сравнивает оба случая.

```
На дешёвой операции (сложение) накладные расходы параллелизма перекрывают выигрыш.
Тяжёлая операция, синхронно          : 339 мс
Тяжёлая операция, Parallel.For      : 90 мс (ускорение 3.77x)
Тяжёлая операция, Partitioner       : 161 мс (ускорение 2.11x)
Результаты совпадают: True
```

### Часть 7.5. Сравнение результатов

Суммы, минимумы, максимумы и средние всех четырёх способов печатаются рядом и
сравниваются; выводятся строки `Суммы совпадают: True` и
`Средние совпадают: True`.

## Ключевые выводы

1. На дешёвой операции (`+`) `Parallel.For` на 10 млн элементов **медленнее**
   синхронного цикла: накладные расходы на запуск потоков и разбиение данных
   перекрывают выигрыш.
2. На тяжёлой операции — ускорение 3.77x, то есть почти линейное на 8 ядрах.
3. Статическое разбиение на число ядер (`Partitioner`) даёт 2.11x: хвост
   последнего диапазона и синхронизация съедают часть выигрыша.
4. Вывод: **параллелизм оправдан только тогда, когда работа на элемент заметно
   тяжелее накладных расходов**. Это главный практический результат задания.
5. Корректность проверяется сравнением с синхронным вариантом, а не «на глаз».
