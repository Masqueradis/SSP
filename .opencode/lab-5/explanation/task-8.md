# Задание 8 — Producer-Consumer: три реализации

**Проект:** `Lab5/Task8` · **Запуск:** `cd Lab5/Task8 && dotnet run`
**Источник:** `ЛАБ_5Многопоточ.docx`, раздел «Реализация Producer-Consumer с использованием Semaphore»

## Что делает программа

Один и тот же сценарий (2 производителя, 3 потребителя, буфер 5, 25 элементов)
реализован тремя способами. Для каждого печатается журнал событий и итоговая
сверка: произведено = потреблено, в буфере 0, потери и дубли нет.

**Все три реализации используют `CancellationTokenSource`:** отмена
разблокирует потоки, ожидающие семафор, поэтому программа всегда завершается
и не зависает.

### Часть 8.1. SemaphoreSlim (empty/filled) + Mutex

Классическая реализация из методики:

* `_emptySlots = new SemaphoreSlim(5, 5)` — свободные места;
* `_filledSlots = new SemaphoreSlim(0, 5)` — занятые места;
* `Mutex` — защита самой очереди.

```
[Producer 1] Добавлен элемент: 81. В буфере: 1 элементов.
[Producer 2] Добавлен элемент: 89. В буфере: 2 элементов.
[Consumer 2] Извлечен элемент: 81. В буфере: 1 элементов.
[Consumer 1] Извлечен элемент: 89. В буфере: 0 элементов.
[Producer 1] Добавлен элемент: 6. В буфере: 1 элементов.
Произведено 25, потреблено 25, в буфере осталось 0, сведено: True
```

Порядок действий производителя: дождаться свободного места → взять `Mutex` →
положить в очередь → отпустить `Mutex` → `_filledSlots.Release()`.
Потребитель делает симметрично.

### Часть 8.2. Monitor.Wait / Pulse

То же самое, но без семафоров: буфер — обычный `Queue<T>` под `lock`, а
ожидание выполняется через `Monitor.Wait` / `Monitor.PulseAll`. Разница в том,
что здесь **невозможна потеря сигнала** (проверка условия и ожидание
выполняются под тем же `lock`), тогда как с семафорами лишний `Release` может
разбудить поток «впустую».

### Часть 8.3. ConcurrentQueue без внешней синхронизации

Коллекция `ConcurrentQueue<T>` уже потокобезопасна, поэтому семафоры и `Mutex`
не нужны вовсе. `TryDequeue` возвращает `false`, когда очередь пуста, и
потребитель просто делает паузу.

## Ключевые выводы

1. Все три реализации дают одинаковый результат: 25 = 25, буфер пуст, потерь нет.
2. `SemaphoreSlim` — когда нужен счётчик одновременных операций (в том числе
   между процессами через `Semaphore`).
3. `Monitor.Wait/Pulse` — когда состояние сложное и важно гарантировать отсутствие
   потери сигнала.
4. `ConcurrentQueue` — самый короткий код, когда достаточно коллекции без
   ограничения размера буфера.
5. Во всех случаях отмена обязана быть «просочиной» в каждое ожидание,
   иначе потоки останутся висеть на семафоре.
