# Задание 1 — Создание и управление потоками (Thread)

**Проект:** `Lab5/Task1` · **Запуск:** `cd Lab5/Task1 && dotnet run`
**Источник:** `МногопотАинхПрогр.docx`, задание 1

## Что делает программа

Показывает, что такое поток в .NET, как передать в него данные, как дождаться
завершения и почему приоритеты потоков на Linux не дают эффекта.

### Часть 1.1. Создание потока и Join

Создаётся дочерний поток, который печатает пронумерованные шаги, главный поток
делает то же самое. Видно, что строки двух потоков чередуются произвольно — это
и есть параллельное выполнение. `Join()` блокирует главный поток до завершения
дочернего, о чём программа сообщает отдельной строкой.

```
[Главный поток 1] шаг 3
[Дочерний поток 4] шаг 3
[Главный поток 1] шаг 4
[Дочерний поток 4] шаг 4
Join() вернул управление: дочерний поток завершён.
```

### Часть 1.2. Три способа передачи параметров

| Способ | Как сделано |
|--------|-----------|
| `ParameterizedThreadStart` | `new Thread(obj => ...)` + `Start(value)` |
| Захват переменной (лямбда) | замыкание видит переменную внешнего метода |
| `ThreadStart` без параметров | поле класса или локальная функция |

Важное отличие: лямбда **захватывает** переменную, поэтому все её изменения видны
потоку; `ParameterizedThreadStart` передаёт **значение** копией.

### Часть 1.3. Три потока одновременно

Три потока печатают числа от 1 до 10 с задержкой 200 мс. Вывод идёт тремя
перемешанными колонками — наглядное доказательство, что `Thread.Sleep` в одном
потоке не мешает остальным.

### Часть 1.4. Гонка данных (race condition)

Общий счётчик `int _counter` увеличивается в четырёх потоках без синхронизации.
Результат **меньше ожидаемого**: `counter++` — это три операции (чтение, сложение,
запись), и между ними другой поток успевает вклиниться.

Затем тот же код с `lock` даёт ровно ожидаемое значение. Это сравнение и есть
доказательство необходимости синхронизации.

### Часть 1.5. Приоритеты потоков

Потокам назначаются `ThreadPriority` от `Lowest` до `Highest`. Затем программа
читает реальные значения `nice` из `/proc/self/task/<tid>/stat` для каждого потока
(идентификатор берётся через P/Invoke `libc gettid`).

**Результат на Linux: у всех потоков `nice` равен 0, независимо от приоритета .NET.**
Причина: в Linux .NET не транслирует `Thread.Priority` в `nice`. Планировщик
Linux оценивает приоритет по значению `nice`, а установить его из managed-кода
можно только через `setpriority` или внешнюю утилиту.

Вывод: приоритеты потоков — понятие в основном Windows. В .NET 6+ на Windows
приоритеты тоже вырождены в диапазон, поэтому на это свойство нельзя полагаться.

## Ключевые выводы

1. `Thread` — настоящий выделенный поток ОС, его создание дорого (~1 МБ стека).
2. `Join` — единственный способ дождаться завершения; без него программа может
   завершиться, не досчитав результат.
3. `lock` обязателен для любого общего изменяемого состояния.
4. Приоритеты потоков на Linux не влияют на планирование.
