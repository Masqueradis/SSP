# Testing Guide — Лабораторная работа 5

**Темы:** потоки и пул потоков, `Task`/`async`/`await`, синхронизация
(`lock`, `Mutex`, `SemaphoreSlim`, `CancellationToken`), паттерн
Producer-Consumer, взаимоблокировки

Пошаговая инструкция: что запустить, что должно быть выведено на экран и как
продемонстрировать работоспособность преподавателю.

Проверено на **.NET 10** (`dotnet --version` → 10.0.112), Linux x64, 8 логических ядер.
Все проекты — в `Lab5/Task1` … `Lab5/Task11`, каждое задание — самостоятельный
консольный проект. Задания 12–16 (TPL/PLINQ) относятся к лабораторной работе 6
и лежат в `Lab6/Task12` … `Lab6/Task16` (см. `.opencode/lab-6/testing-guide.md`).

> Если на машине преподавателя только SDK 8.0, нужно заменить
> `<TargetFramework>net10.0</TargetFramework>` на `net8.0` во всех `.csproj`.
> Используемый API доступен и в `net8.0`, кроме `PeriodicTimer` (тоже с .NET 6)
> и `GetWindowedStatistics` — смена TFM безопасна.

> **Важно про Linux/Windows:** `Task1` и `Task10` читают приоритеты потоков из
> `/proc` через P/Invoke `libc` и печатают, что на Linux приоритеты .NET
> не влияют на планирование. На Windows эти строки будут другими — это не
> ошибка, а исследуемое поведение платформы.

## 2. Что показывать преподавателю (по заданиям)

### Задание 1 — `Thread` (≈10 с)

Ключевые строки для демонстрации:

* чередование вывода двух потоков — доказательство параллельности;
* `Join() вернул управление: дочерний поток завершён.`;
* три способа передачи параметров подписаны отдельно;
* **главное:** гонка данных даёт счётчик меньше ожидаемого, а тот же код
  под `lock` — ровно ожидаемое. Попросите преподавателя сравнить два числа;
* вывод `nice` всех потоков = 0 при заданных `ThreadPriority`.

### Задание 2 — `ThreadPool` (≈20 с)

Покажите, что 20 задач выполняются всего на 4–5 потоках одновременно, а
1000 задач используют ограниченное число потоков. Сравните с 1000
выделенными `Thread` из того же задания.

### Задание 3 — `Task` и `async/await` (≈20 с, таймер занимает 10 с)

Главная строка: `Суммарное время: 1502 мс (сумма задержек = 3600 мс)`.
Покажите, что идентификаторы потоков у трёх «загрузок» **разные** — значит
потоки действительно освобождались на время `await`.

### Задание 4 — синхронизация (≈10 с)

Ключевое: `Итоговое значение: 0 (ожидалось 0)` в SafeCounter и то, что в
`SemaphoreSlim(3)` счётчик одновременного присутствия **никогда не превышает 3**.

### Задание 5 — параллельные коллекции (≈20 с, TTL-кэш ждёт 13 с)

Покажите TTL-кэш: `промах: ключ-1 (TTL истёк, элемент удалён)` и статистику
попаданий/промахов. Обратите внимание на строку: `ConcurrentDictionary сам по
себе не хранит время жизни, TTL проверяется вручную`.

### Задание 6 — `CancellationToken` (≈10 с)

Покажите `CreateLinkedTokenSource`: сработал таймаут — при этом
`manual.IsCancellationRequested = False`, а `linked = True`. Это доказывает
объединение источников.

### Задание 7 — комплексная задача (≈30 с, массив 10 млн элементов)

**Обязательно сравните два числа:**

```
Тяжёлая операция, синхронно     : 339 мс
Тяжёлая операция, Parallel.For : 90 мс (ускорение 3.77x)
```

и обратный случай — на дешёвой операции (`+`) `Parallel.For` медленнее
синхронного. Это главный вывод задания: параллелизм оправдан не всегда.

Изменить размер массива: `dotnet run -- 5000000` (по умолчанию 10 000 000,
размер печатается в заголовке).

### Задание 8 — Producer-Consumer (≈30 с)

Три реализации подряд: семафоры + `Mutex`, `Monitor.Wait/Pulse`,
`ConcurrentQueue`. Для каждой ищите строку
`Произведено 25, потреблено 25, в буфере осталось 0, сведено: True`.

### Задание 9 — анализ Producer-Consumer (≈60 с)

Таблица 9.1 (размер буфера 2 / 5 / 10) и 9.2 (2+3 / 3+3 / 4+4). Три
наблюдения, которые нужно прокомментировать:

1. `max занятость = capacity` — семафоры не дают переполнить буфер;
2. **потреблено одинаково** во всех конфигурациях — скорость задают потребители;
3. произведено растёт с размером буфера — большой буфер даёт стартовый запас.

### Задание 10 — взаимоблокировка (два режима!)

```bash
dotnet run              # безопасный режим: программа завершается
dotnet run -- deadlock  # НАСТОЯЩИЙ дедлок: программа зависнет намеренно
```

Запускайте `deadlock` только под присмотром и только если готовы прервать
(в Visual Studio: Break All → Parallel Stacks, на Linux: `Ctrl+C`).

В безопасном режиме покажите: граф ожидания (`Thread1 -> lockA -> ждёт lockB`),
затем «единый порядок блокировок» (взаимоблокировка невозможна) и
`Monitor.TryEnter` с таймаутом (вместо зависания — диагностика).

### Задание 11 — `Mutex` (≈20 с)

Покажите: реентерабельность (счётчик 1 → 2 → 0) и межпроцессную блокировку —
дочерний процесс ждёт мьютекс, главный освобождает, дочерний входит.
Отдельный сценарий: `AbandonedMutexException` после аварийного выхода
владельца.

Обратите внимание: различие `Local\`/`Global\` — понятие Windows; на Linux
области имён нет. Это отражено в выводе.


## 3. Полный прогон (для отчёта)

```bash
cd /home/masqueradis/ssp/Lab5
mkdir -p /tmp/lab5-check
for i in $(seq 1 11); do
  dotnet build -v q --nologo Task$i/Task$i.csproj > /tmp/lab5-check/Task$i.build.log 2>&1
  echo "Task$i build=$?"
  (cd Task$i && timeout 300 dotnet run --no-build < /dev/null > /tmp/lab5-check/Task$i.run.log 2>&1)
  echo "Task$i run=$?"
done
```

Ожидается: все `build=0`, все `run=0`, в каждом логе есть строка
`ВЫПОЛНЕНО`.

## 4. Частые проблемы

| Симптом | Причина и решение |
|---------|-------------------|
| `dotnet: command not found` | не установлен .NET SDK; нужен 8.0 или 10.0 |
| `Process terminated` после `dotnet run -- deadlock` | так и задумано: это настоящая взаимоблокировка |
| Задание 7 долго работает | 10 млн элементов по умолчанию; уменьшить: `dotnet run -- 1000000` |
| Задание 9 долго работает | это 6 прогонов Producer-Consumer, так и задумано |
| Числа отличаются от документации | замеры времени зависят от машины; **совпадение результатов** важно, время — нет |
| `AbandonedMutexException` в `Task11` | ожидаемое поведение: показывайте его как успешную демонстрацию |
| На Windows нет вывода `nice` | вывод специфичен для Linux, см. врезку в начале |
