## 1. Что такое MQTT и в чем его преимущества для IoT?

**MQTT** (Message Queuing Telemetry Transport) — лёгкий протокол обмена сообщениями
для IoT, работающий по модели «издатель–подписчик» (Publish–Subscribe) поверх TCP.

Ключевые понятия: **брокер** (сервер, принимает и маршрутирует сообщения),
**издатель** (Publisher), **подписчик** (Subscriber), **топик** (иерархический
канал обмена, например `iot/devices/simulated/data`).

Преимущества для IoT:

- **Малый размер заголовка** (от 2 байт) и низкий расход трафика — важно для
  устройств со слабым каналом связи;
- **Модель pub/sub** — устройство не знает о получателях, добавление
  потребителей данных не требует изменения прошивки датчика;
- **Уровни доставки QoS 0/1/2** — выбор компромисса между скоростью и
  гарантией;
- **Работа через прокисы/нестабильные сети**, механизм Keep Alive и
  флаг Retained message (последнее состояние доступно новому подписчику);
- **QoS-подписка на брокере**: сообщения копятся для офлайн-клиента
  (clean session = false).

В нашей лабораторной: `Task2` подключается к `broker.hivemq.com`, `Task3`
публикует JSON-телеметрию на `test.mosquitto.org` в топик
`iot/devices/simulated/data`.

## 2. В чем разница между QoS 0, 1 и 2?

| Уровень | Название | Гарантия | Цена |
|---------|----------|----------|------|
| QoS 0 | At most once | Сообщение доставляется **не более одного раза**: «отправил и забыл», подтверждения нет | Минимальная задержка и нагрузка; терять сообщения можно |
| QoS 1 | At least once | Сообщение доставляется **хотя бы один раз**: отправитель повторяет его, пока не получит PUBACK | Возможны **дубликаты** (если подтверждение потерялось) |
| QoS 2 | Exactly once | Доставляется **ровно один раз**: четырёхшаговый обмен (PUBLISH → PUBREC → PUBREL → PUBACK) | Максимальные накладные расходы, самая большая задержка |

Правило выбора: телеметрия датчиков обычно идёт с QoS 1 (дубликаты приемлемы,
пропуски — нет), редкие критичные команды — QoS 2, разовые показания в
высокочастотном потоке — QoS 0.

В наших проектах применён **QoS 1 (AtLeastOnce)**: подписка в `Task2`/`Listener`
и публикация телеметрии в `Task3`.

## 3. Почему важен суточный цикл в моделировании датчика?

Реальные помещения не существуют в «статичных» условиях: температура и
освещённость меняются в течение суток. Без суточного цикла симулятор выдавал бы
машинно-правдоподобный, но **нереалистичный** ряд, и алгоритмы, обучающиеся или
реагирующие на данные (автоматика, ML-модели), работали бы в условиях,
которых не встретят в жизни.

В коде `Task3` суточный цикл реализован синусоидой:

```csharp
double dailyCycle = 5.0 * Math.Sin(2 * Math.PI * (now.Hour + now.Minute / 60.0) / 24.0);
```

Она даёт плавные ночные/дневные колебания ±5 °C. Аналогично освещённость
считается от локального времени: днём до ~1000 лк (форма `sin` от 6:00 до
18:00), ночью ~50 лк, плюс +350 лк при включённом свете.

Суточный цикл также важен для **отладки логики реагирования**: можно
воспроизвести «пики» и «спады» и убедиться, что алгоритм не ложно срабатывает
ночью.

## 4. Как влияет открытие двери на температуру и влажность?

Открытие двери соединяет помещение с улицей/коридором, и идёт **интенсивный
обмен воздухом** (конвекция). В симуляторе (`Task3`, `ReadData`):

```csharp
if (_isDoorOpen)
{
    double outsideTemp = 15.0 + (_random.NextDouble() * 2 - 1) * 3.0;
    tempChange += (outsideTemp - _temperature) * 0.02 * deltaMinutes;
    humidityChange += (40 - _humidity) * 0.01 * deltaMinutes;
}
```

- **Температура** тянется к уличной (≈15 ± 3 °C): скорость изменения
  пропорциональна разнице температур — чем холоднее на улице, тем быстрее
  помещение остывает;
- **Влажность** тянется к уличной (≈40 %): если на улице суше — влажность
  падает, если влажнее — растёт;
- эффект **пропорционален времени** (`deltaMinutes`): дверь, открытая минуту,
  влияет сильнее, чем открытая секунду.

Практическое следствие для лаборатории: открыв дверь (`door → open`), мы
наблюдаем падение температуры ниже 22 °C и срабатывание гудка.

## 5. Почему влажность коррелирует с температурой?

Физическая связь: **тёплый воздух содержит больше воды** (по абсолютному
содержанию), а относительная влажность зависит и от температуры, поскольку
емкость воздуха по отношению к водяному пару растёт с нагревом.

В симуляторе корреляция заложена прямо в формулу:

```csharp
double humidity = 60 + (temperature - _baseTemperature) * 2 + шум;
```

Отклонение температуры от базовой умножается на коэффициент 2: нагрев
(обогреватель, люди, свет) сопровождается ростом влажности (дыхание, испарения),
а охлаждение — её снижением. Такая взаимосвязь делает модель правдоподобной:
датчик в реальности не выдаёт независимые случайные числа, а связанные величины.

## 6. Какие форматы данных можно использовать для IoT и их плюсы/минусы?

| Формат | Плюсы | Минусы |
|--------|-------|--------|
| **JSON** | Универсальный, человекочитаемый, поддерживается везде, схема расширяема (metadata) | Избыточен (кавычки, имена полей), жрёт трафик и CPU на парсинг |
| **CSV** | Прост, компактен, удобен для таблиц и выгрузок | Нет структуры вложенных полей, хрупок к изменению порядка/состава колонок |
| **XML** | Строгая схема (XSD), самодокументируем | Ещё более избыточен, тяжёл для слабых устройств |
| **CBOR** | Бинарный «JSON», компактный, стандарт IETF | Мало инструментов, трудно отлаживать глазами |
| **MessagePack** | Компактный бинарный, быстрый парсинг | Нечеловекочитаем, нужна библиотека на устройстве |
| **Protocol Buffers / FlatBuffers** | Очень компактные, схема версионируется, быстрые | Нужен компилятор схемы, схему надо синхронизировать между устройством и облаком |
| **Raw bytes / битовое поле** | Минимальный оверхед, фиксированный формат | Нет самодокументации, любое изменение — ломает совместимость |

В лабораторной выбран **JSON** (`System.Text.Json`, camelCase, без отступов —
экономия трафика): он нагляден для защиты и подходит облачным шлюзам (Azure IoT
Hub, AWS IoT Core принимают JSON «из коробки»).

## 7. Как обеспечить отказоустойчивость в IoT-системе?

- **Локальное буферизация/очередь**: если сеть недоступна, датчик копит
  показания (например, в файле) и отправляет при восстановлении связи;
- **Keep Alive и авто-переподключение**: в `Task3` реализован
  `ReconnectMqttClient()`, при обрыве публикация не роняет программу;
- **QoS 1/2** — повторная доставка при потере подтверждения;
- **Идемпотентность обработки** — приёмник должен корректно переживать
  дубликаты (QoS 1);
- **Ретейн-сообщения** — брокер хранит последнее состояние, вновь
  подключившийся потребитель сразу узнаёт актуальные данные;
- **Таймауты, валидация данных, резервные брокеры/шлюзы**, мониторинг
  «живости» устройства (онлайн-статус, датчики сигнализируют отсутствие
  данных);
- **Защита канала** (TLS, порт 8883, сертификаты/симметричные ключи устройств)
  и ограничение прав топика (ACL): отказ — это ещё и безопасность.

В нашей программе: при недоступности брокера она продолжает работать
(«автономный режим»), пишет данные в файл и пытается переподключиться.

## 8. Что такое «держать сессии» (Keep Alive) в MQTT?

**Keep Alive** — интервал (в секундах), который клиент договаривается с
брокером при CONNECT. За это время клиент обязан отправить брокеру любой MQTT
пакет (обычно PINGREQ), иначе брокер считает клиент мёртвым и **разрывает
TCP-соединение**, «осиротевшие» подписки отписывает.

- Значение задаётся в `MqttClientOptionsBuilder().WithKeepAlivePeriod(...)`;
  в `Task3` — **60 секунд**;
- Keep Alive = 0 — отключить (соединение не проверяется);
- Меньший интервал → быстрее обнаружение обрыва, но больше служебного трафика;
  для батарейных устройств выбирают десятки секунд;
- Плюс **Clean Session**: при `false` брокер хранит подписки и непринятые
  сообщения клиента, давая эффект «держания сессии» между переподключениями.

## 9. Как проверить, что данные дошли до облачного сервера?

Способы (от простого к сложному):

1. **Второй MQTT-клиент-подписчик** — независимое приложение подписывается на
   тот же топик и печатает входящие сообщения. Если симулятор в одном терминале,
   а подписчик в другом видит сообщения — данные дошли до брокера-облака.
   В лабораторной это проект **`Lab7/Listener`**:
   ```bash
   cd Lab7/Listener && dotnet run
   ```
   Приём полного JSON с полями `deviceId`, `temperature`, `metadata...` и есть
   доказательство доставки; программа печатает
   `=== ДОСТАВКА В ОБЛАКО ПОДТВЕРЖДЕНА ===`.
2. **Веб-клиенты брокера**: MQTT Explorer, MQTTX, или веб-консоль
   `HiveMQ MQTT Web Client` (для `broker.hivemq.com`), ввести брокер, топик,
   увидеть поток сообщений.
3. **Консольные утилиты**: `mosquitto_sub -h test.mosquitto.org -t "iot/devices/simulated/data"`.
4. **Код приёма на самом устройстве** — эхо-сообщение от брокера (в `Task2`
   мы подписались на свой же `test/topic` и видим свои 5 сообщений).
5. **На стороне облака** — в панели IoT-платформы (Azure IoT Hub →
   «Device telemetry», AWS IoT Core → MQTT test client / Rules) смотреть
   входящий поток.

## 10. Какие еще протоколы используются в IoT?

- **CoAP** (Constrained Application Protocol) — REST поверх UDP, для
  сверхслабых устройств, запрос-ответ без постоянного соединения;
- **HTTP/HTTPS (REST, WebSocket)** — универсален, но тяжёл для датчиков;
- **AMQP** — надёжная очередь сообщений, используется в облачных шлюзах
  (Azure Event Hub);
- **MQTT-SN** — «датчикный» вариант MQTT поверх UDP/Bluetooth для устройств
  без TCP;
- **LoRaWAN, NB-IoT, Zigbee, Z-Wave, Bluetooth LE, Wi-Fi** — уровни
  транспорта/радиодоступа для устройств;
- **Modbus, BACnet, OPC UA** — промышленные протоколы опроса оборудования,
  часто шлюзуются в MQTT;
- **DDS** — распределённая подписка для реального времени (робототехника,
  автопилоты);
- **LwM2M / CoAPS** — управление и обновление прошивок устройств.

Частая архитектура: датчик → (LoRa/Zigbee) → шлюз → **MQTT** → облако →
приложение.
