# Задание 14 — PLINQ для анализа данных

**Проект:** `Lab6/Task14` · **Запуск:** `cd Lab6/Task14 && dotnet run`
**Источник:** `ЛабПарПрограм.docx`, задание 3 «PLINQ для анализа данных»

## Что делает программа

Полный набор операций PLINQ на массиве из 1 000 000 элементов и сравнение
с обычным LINQ, `Parallel.ForEach` и последовательным циклом.

### Часть 14.1. AsParallel и базовый запрос

```
var evens = numbers.AsParallel().Where(x => x % 2 == 0);
```

Сравнивается время LINQ и PLINQ на одном и том же предикате. На коротких
запросах PLINQ проигрывает: накладные расходы на разбиение и слияние
не окупаются.

### Часть 14.2. Where + Select

Комбинация фильтрации и проекции. Показано, что порядок элементов после
PLINQ **не сохраняется**, а `Select` может быть вытолкнут вниз по конвейеру
(fusion), что уменьшает количество проходов.

### Часть 14.3. OrderBy

`OrderBy` в PLINQ даёт **отсортированный** результат (это единственная
операция, которая восстанавливает порядок), но требует сортировки блоков
и их слияния — то есть полного прохода по всем данным. На этом примере
показано, что PLINQ для глобальной сортировки дороже, чем кажется.

### Часть 14.4. GroupBy

Группировка по признаку и подсчёт элементов в группах
(например, по последней цифре числа). Отдельно показан `ToLookup`, который
для этой задачи эффективнее `GroupBy(...).ToDictionary()`.

### Часть 14.5. Aggregate

Агрегация через `Aggregate` с seed и функцией-аккумулятором, а также
специализированные `Sum`, `Count`, `Min`, `Max`, `Average`.

### Часть 14.6. WithCancellation и WithDegreeOfParallelism

```
var q = source.AsParallel()
             .WithCancellation(cts.Token)
             .WithDegreeOfParallelism(4)
             .Where(...);
```

Показывается, что отмена PLINQ-запроса прерывает вычисление, а
`WithDegreeOfParallelism` ограничивает число потоков — полезно, чтобы
не занимать все ядра.

### Часть 14.7. Сравнение с Parallel.ForEach

PLINQ удобен для цепочек операций над коллекциями, но для чистой нагрузки
на CPU `Parallel.ForEach` обычно выигрывает: у PLINQ есть дополнительный слой
абстракции (дерево операций) и накладные расходы на его построение.
Фактические времена сравнения печатаются, и вывод формулируется
**по фактическим замерам**, а не в пользу PLINQ по умолчанию.

## Ключевые выводы

1. `AsParallel()` включает параллельное выполнение, но на коротких запросах
   PLINQ проигрывает из-за накладных расходов.
2. Порядок элементов не сохраняется; его восстанавливает только `OrderBy`.
3. `WithCancellation` и `WithDegreeOfParallelism` — основные инструменты
   управления параллелизмом в PLINQ.
4. `Parallel.ForEach` обычно быстрее PLINQ для чистой вычислительной нагрузки.
5. `WithMergeOptions(ParallelMergeOptions.FullyBuffered)` возвращает порядок
   и снижает накладные расходы на слияние — полезный компромисс.
