# Задание 16 — Индивидуальное задание (все 7 вариантов)

**Проект:** `Lab6/Task16` · **Запуск:** `cd Lab6/Task16 && dotnet run -- <номер 1..7>`
**Источник:** `ЛабПарПрограм.docx`, задание 5 «Комплексная обработка изображений» + таблица индивидуальных вариантов

## Что делает программа

Один проект со всеми семью индивидуальными вариантами. Номер выбирается
аргументом командной строки; без аргумента выполняется вариант 1. Каждый
вариант содержит **собственный приём распараллеливания**, последовательный
эталон для сверки, замер времени и вывод с объяснением приёма.

---

## Вариант 1 — Обработка больших массивов данных

Суммирование, поиск максимума и минимума на массиве из 2 000 000 элементов.

Приём: результат разделён по индексу — каждый поток пишет в свой ячеечный
массив, свод выполняется после цикла. Синхронизации внутри цикла нет.

```
Сумма, минимум, максимум  последовательно 249.5 мс, параллельно 101.0 мс, ускорение 2.47x
Сумма: 19,999,438,004.93, минимум: 0.0000, максимум: 1000.0000
```

## Вариант 2 — Параллельная фильтрация коллекций (PLINQ)

Два пользовательских условия и проекция на 5 000 000 числах.

```
Два условия и проекция  последовательно 50.4 мс, параллельно 100.0 мс, ускорение 0.50x
Сумма отрицательных чисел, кратных 3: -416,876,292,318
Отобрано значений по условию x % 1000 == 0: 5,056
```

**Честный вывод:** здесь PLINQ **проиграл** в 2 раза. Три лёгких операции
на 5 млн элементах не дают достаточно работы, чтобы окупить разбиение и
слияние блоков. Это ценный отрицательный результат: PLINQ оправдан не
всегда.

## Вариант 3 — Матричные вычисления

Умножение и транспонирование матриц 600×600.

```
Умножение матриц      последовательно 1695.1 мс, параллельно 412.9 мс, ускорение 4.10x, результаты совпали
Транспонирование      последовательно    4.2 мс, параллельно   2.8 мс, ускорение 1.48x, результаты совпали
```

Приём: строки результата независимы, поэтому `Parallel.For` по строкам даёт
почти линейное ускорение. Матрицы хранятся построчно — это важно для кэша.

## Вариант 4 — Обработка изображений

Оттенок серого, инверсия, размытие 3×3 на изображении 1000×1000.

```
Три фильтра подряд   последовательно  73.8 мс, параллельно  46.0 мс, ускорение 1.60x, результаты совпали
Размытие 3x3         последовательно  17.2 мс, параллельно   5.9 мс, ускорение 2.94x, результаты совпали
```

Приём: строки независимы, обрабатываются пачками через `Partitioner`.
Буфер результата отделён от исходного, поэтому размытие не читает уже
изменённые пиксели — иначе результат был бы неверным.

## Вариант 5 — Анализ текстовых данных

Подсчёт слов и поиск вхождений на сгенерированном тексте ~8 МБ (96 676 строк).

```
Подсчёт слов и частот  последовательно 116.1 мс, параллельно 54.0 мс, ускорение 2.15x, результаты совпали
Всего слов: 800,409, уникальных: 8
  дедлок 100,356 · задача 100,405 · многопоточность 100,034 · синхронизация 100,498
Строк со словом "дедлок": 60,391 за 17.5 мс
```

Приём: каждый диапазон строк считает частоты в **свой** словарь, словари
соединяются после цикла. Общий словарь под `lock` дал бы правильный, но
намного более медленный результат.

## Вариант 6 — Численные методы

Интегрирование методом Симпсона (20 млн точек), поиск минимума функции
(4 млн точек), численная производная.

```
Интеграл Симпсона    последовательно 377.8 мс, параллельно 134.5 мс, ускорение 2.81x, результаты совпали
Расхождение с последовательным расчётом: 7.43E-006
Поиск минимума       последовательно  75.9 мс, параллельно  17.8 мс, ускорение 4.27x, результаты совпали
Численная производная последовательно   0.8 мс, параллельно   0.9 мс, ускорение 0.83x, результаты совпали
```

Важная деталь: `double` сравнивается **по относительной погрешности**
(7.43E-06), а не по точному равенству. Порядок обхода меняет округление
при сложении 20 млн слагаемых, поэтому точное `==` дало бы ложную ошибку.
Средний узел последнего блока получает вес 1, поэтому число интервалов
выбирается чётным.

## Вариант 7 — Сортировка и поиск

Сортировка 5 000 000 чисел и параллельный поиск первого вхождения.

```
Array.Sort vs параллельное слияние  последовательно 465.9 мс, параллельно 257.2 мс, ускорение 1.81x, результаты совпали
То же с компаратором               последовательно 350.4 мс, параллельно 228.3 мс, ускорение 1.53x, результаты совпали
Поиск первого вхождения            последовательно   2.2 мс, параллельно   3.1 мс, ускорение 0.72x, результаты совпали
QuickSelect нашёл 5000689-й элемент за 29.3 мс (полная сортировка 465.9 мс)
```

Приём: массив делится на блоки по числу ядер, каждый сортируется своим
потоком, затем блоки сливаются попарно. `Array.Sort` внутри уже делает
нечто подобное, поэтому выигрыш скромный. А вот параллельный поиск дал
**ускорение 0.72x** — проигрыш: 2 мс на 5 млн элементов не окупают
накладные расходы. Зато `QuickSelect` (29.3 мс) в 16 раз быстрее полной
сортировки, потому что не сортирует целиком.

## Ключевые выводы по всем вариантам

1. Распараллеливание даёт выигрыш от 1.5x до 4.3x **только** на тяжёлой
   работе на элемент.
2. Лёгкие операции (PLINQ-фильтрация, поиск, производная) дают проигрыш
   0.50x–0.83x — это измерено, а не предположено.
3. Каждый вариант сверяется с последовательным эталоном: расхождение
   результатов означало бы ошибку параллелизма.
4. `double` требует сравнения по относительной погрешности.
5. Общий вывод: параллелизировать надо **тяжёлое и независимое**; лёгкое
   и мелкое лучше оставить последовательным.
