# Задание 15 — Разделение данных и агрегация

**Проект:** `Lab6/Task15` · **Запуск:** `cd Lab6/Task15 && dotnet run`
**Источник:** `ЛабПарПрограм.docx`, задание 4 «Разделение данных и агрегация»

## Что делает программа

Обработка изображения (RGB-фильтр по яркости) шестью способами параллельной
обработки, со сравнением результатов и времени.

### Часть 15.1. Последовательная обработка

Эталон: последовательный проход по строкам с замером `Stopwatch`. Результат
этого прогона сохраняется и далее используется как образец для проверки
корректности всех параллельных вариантов (`Совпало с эталоном: True`).

### Часть 15.2. Partitioner.Create

```
Partitioner.Create(0, Height, 15)
```

Диапазон строк делится на блоки по 15 строк. Блоков больше, чем потоков,
поэтому перекос гасится. Печатается фактическое число частей.

### Часть 15.3. Parallel.For и Parallel.ForEach

Сравниваются два способа обхода: по индексу (`Parallel.For`) и по коллекции
диапазонов (`Parallel.ForEach`). Результаты совпадают с эталоном.

### Часть 15.4. Собственный разделитель с локальной очередью потока

Реализован `OrderableRangePartitioner : Partitioner<Range>` с
`SupportsDynamicPartitions = true`:

* диапазоны кладутся в общую `ConcurrentQueue<Range>`;
* у каждого потока свой `ThreadLocal<Stack<Range>>`;
* когда локальный стек пуст, поток забирает из общей очереди **пачку** из
  4 диапазонов и дальше работает только со своим стеком.

Это локальное буферирование снижает конкуренцию на общей очереди. Счётчики
выводятся явно, поэтому утверждение проверяемо, а не декларативно:

```
Пополнений локальной очереди: 180, взято из неё: 540, напрямую из общей: 0
```

То есть 100 % изъятых диапазонов прошли через локальные очереди — локальный
буфер действительно работает.

### Часть 15.5. Влияние размера блока

Перебираются размеры блока 1, 5, 15, 45, 150, 900 и печатается время каждого.
Вывод, который печатает программа: слишком мелкие блоки дают накладные расходы
на разбиение, слишком крупные — плохую балансировку; оптимум приходится
на средние значения.

### Часть 15.6. Неравномерная нагрузка

Часть строк обрабатывается заметно дольше остальных (искусственные задержки
для отдельных диапазонов). Статическое разбиение на число ядер даёт плохое
время, потому что последний диапазон определяет всё время цикла; разделитель
с общей очередью справляется лучше.

### Часть 15.7. Пустой вход

`.NET` требует различающихся границ диапазонов, а собственные диапазоны при
пустом входе просто не порождаются. Программа явно отсекает пустой вход и
печатает об этом сообщение, чтобы вел себя предсказуемо.

## Ключевые выводы

1. `Partitioner.Create` с блочным разделением — базовый способ убрать
   синхронизацию из тела цикла.
2. При неравномерной нагрузке статическое разбиение на число ядер проигрывает
   динамическому: хвост последнего диапазона определяет всё время.
3. Собственный `IPartitioner` позволяет добавить локальное буферирование и
   снизить конкуренцию (в реализации — пачками по 4 диапазона).
4. Любой параллельный вариант обязан сверяться с последовательным эталоном.
5. Размер блока — компромисс между накладными расходами разбиения и
   балансировкой нагрузки.
