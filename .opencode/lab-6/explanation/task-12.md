# Задание 12 — Введение в параллельные циклы

**Проект:** `Lab6/Task12` · **Запуск:** `cd Lab6/Task12 && dotnet run`
**Источник:** `ЛабПарПрограм.docx`, задание 1 «Введение в параллельные циклы»

## Что делает программа

Классический пример из методики: общий массив и общий счётчик, к которому три
потока обращаются одновременно. Показаны пять решений, и для каждого измерена
стоимость. Все пункты используют один массив из 8 000 000 элементов, поэтому
результаты сравниваются напрямую.

### Часть 12.1. Последовательное вычисление

Базовая линия: последовательный проход.

```
Последовательно:  сумма 3,999,645,179.91, мин 0, макс 1000, среднее 499.9556
Время: 121 мс
```

### Часть 12.2. Parallel.For с локальным состоянием диапазона

Перегрузка с `localInit` / `localFinally`: каждому диапазону достаётся
собственный аккумулятор, сведение выполняется один раз после цикла.

```
Parallel.For:     сумма 3,999,645,179.91, мин 0, макс 1000, среднее 499.9556
Время: 65 мс, результат совпал с последовательным расчётом: True
```

### Часть 12.3. Общий ресурс БЕЗ синхронизации: потеря обновлений

Тот же массив суммируется напрямую в общую ячейку.

```
Полученная сумма: 9,676,717,745,570
Ожидаемая сумма: 31,999,996,000,000
Ошибка: 22,323,278,254,430 (69.76%)
```

`shared[0] += i` — это чтение, сложение и запись в три отдельных шага; между
чтением и записью успевает вклиниться другой поток. Потеряно почти 70 %
слагаемых. `Parallel.For` не защищает общие переменные — это остаётся заботой
разработчика.

### Часть 12.4. Общий ресурс С синхронизацией

| Способ | Время | Ошибка |
|---|---|---|
| `lock` на весь расчёт | 785 мс | 0 |
| `Interlocked.Add` | 146 мс | 0 |
| Локальный аккумулятор + сведение после цикла | **17 мс** | 0 |

`lock` корректен, но сериализует всё вычисление и убивает параллелизм.
`Interlocked` корректен и дешевле `lock` в 5.4 раза, но всё равно создаёт точку
конкуренции. Лучший результат — вообще не трогать общий ресурс из тела цикла.

### Часть 12.5. Segmented sieve — практический пример

Решето Эратосфена для чисел до 20 000 000 в четырёх вариантах:

| Вариант | Простых | Время | Ускорение |
|---|---|---|---|
| Последовательное решето | 1 270 607 | 348 мс | 1.00x |
| `Parallel.For`, сведение после цикла | 1 270 607 | 57 мс | 6.12x |
| `Parallel.For`, `lock` раз на сегмент | 1 270 607 | 42 мс | **8.34x** |
| `Parallel.For`, `lock` на каждый простой | 1 270 607 | 77 мс | 4.50x |

Ключевая идея, которую подчёркивает программа: `lock` вокруг общих данных
убивает параллелизм, а **сегментация** (каждый поток обрабатывает свой диапазон
и отмечает простые только в своём сегменте) снимает блокировку. Видно и
обратное: блокировка раз на сегмент (42 мс) дешевле, чем на каждый элемент
(77 мс), — частота блокировок важнее её стоимости.

### Часть 12.6. Сравнение результатов

Все варианты решета обязаны дать одинаковое количество простых чисел:
`Верный ответ: 1,270,607. Все варианты сошлись: True`. Это и есть
доказательство корректности параллельной версии.

## Ключевые выводы

1. `Parallel.For` — самый простой способ распараллелить цикл с известными
   границами.
2. `Parallel.For` **не** защищает общие переменные: без синхронизации теряется
   69.76 % результата.
3. Самая дорогая ошибка — общий изменяемый счётчик под `lock` (785 мс против
   17 мс, разница в 46 раз): он «параллелит» только внешний цикл.
4. `Interlocked` лучше `lock`, но масштабируется плохо.
5. Лучший результат даёт **устранение общих данных**: разделимость по индексу
   или сегментация (8.34x).
6. Параллельные варианты обязаны проверяться сравнением с последовательным.
