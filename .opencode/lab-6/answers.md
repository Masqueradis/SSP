### 1. Что такое Task Parallel Library (TPL) и каковы её основные компоненты?

TPL — набор типов в `System.Threading.Tasks` для структурированного, контролируемого
параллелизма. Появился в .NET 4.

Компоненты:

* **`Task` и `Task<T>`** — единица работы. Есть состояния, отмена, продолжения,
  приоритет, привязка к токену отмены.
* **`TaskScheduler` / `TaskScheduler.Default`** — планировщик (пул потоков);
  `TaskScheduler.FromCurrentSynchronizationContext()` — UI-контекст.
* **`Parallel`** — статические методы `For`, `ForEach`, `Invoke` для данных.
* **`ParallelLoopOptions` / `ParallelOptions`** — `MaxDegreeOfParallelism`,
  `CancellationToken`, `TaskScheduler`.
* **Структурированная отмена** — `CancellationToken` и `CancelAfter`, `CreateLinkedTokenSource`.
* **Локальное состояние итерации** — перегрузки `localInit` / `localFinally`,
  избавляющие от блокировок в теле цикла.
* **Результаты и исключения** — `Task.WhenAll`, `Task.WhenAny`, `Task.Result`,
  `AggregateException`.

Отличие от «сырых» потоков: TPL сам управляет пулом, поддерживает отмену, не требует
`Join` вручную и даёт структуру, которую можно отменить целиком.

### 2. В чём разница между `Parallel.For` и `Parallel.ForEach`?

| | `Parallel.For` | `Parallel.ForEach` |
|---|---|---|
| Источник | диапазон целых `from..to` | коллекция `IEnumerable<T>` |
| Итерация | индекс `i` | сам элемент `x` |
| Разбиение | на диапазоны индексов | на элементы, затем на диапазоны |
| Синтаксис | `Parallel.For(0, n, i => ...)` | `Parallel.ForEach(list, x => ...)` |

Функционально они реализованы одним и тем же планировщиком, различается только
вход. Практическое правило: если есть массив или счётчик — `Parallel.For` (индекс
быстрее и не нужен доступ к элементу), если есть список, `HashSet`, `IEnumerable`
или LINQ-источник — `Parallel.ForEach`. Разница в скорости минимальна, поэтому
выбор диктует удобство, а не производительность.

Дополнительно у обоих есть перегрузка с `ParallelLoopState`, дающая `Break()`
и `Stop()` для досрочной остановки, — она используется в `Lab6/Task13`.

### 3. Чем PLINQ отличается от стандартного LINQ?

PLINQ — это LINQ над `IEnumerable<T>`, помеченных через `AsParallel()`.

Отличия:

* **Параллельное выполнение.** Операции выполняются одновременно над блоками данных.
* **Неизвестный порядок.** Порядок элементов не сохраняется: `OrderBy` сохраняет
  результат сортировки, но не порядок исходных элементов. `Take(5)` без сортировки
  вернёт пять произвольных элементов.
* **Настройка параллелизма.** `WithDegreeOfParallelism`, `WithExecutionMode`,
  `WithMergeOptions`, `WithCancellation`.
* **Другой профиль ошибок.** `AggregateException` вместо исходного исключения
  на верхнем уровне.
* **Дополнительные расходы.** Разбиение и слияние блоков. На коротких запросах
  PLINQ проигрывает последовательному LINQ — это видно в `Lab6/Task14` (пункты 14.1, 14.2).

Вывод: PLINQ хорош для запросов с честными предикатами на больших объёмах.
Для чистой нагрузки на CPU `Parallel.ForEach` обычно быстрее — сравнение в
`Lab6/Task14` (пункт 14.6).

### 4. Какие существуют стратегии разделения данных?

1. **Статическое разбиение.** Диапазон делится на фиксированное число частей, каждая
   обрабатывается один раз. Плюс: нет синхронизации. Минус: перекос, если работа
   неравномерна. Это `Parallel.For(0, cores, core => ...)` в `Lab6/Task16` (вариант 1).
2. **Динамическое разбиение (work stealing).** Разделитель выдаёт следующему потоку
   диапазон только когда тот освободился. Плюс: балансировка. Минус: стоимость
   синхронизации на разделителе. Это режим `Parallel.ForEach` по умолчанию.
3. **Диапазонный `Partitioner` (range partitioner).** `Partitioner.Create(0, n, rangeSize)`
   делит диапазон на блоки заданного размера: их больше, чем потоков, поэтому
   перекос гасится. Применяется в `Lab6/Task15` (пункт 15.2).
4. **Пользовательский `IPartitioner` / `Partitioner<T>`.** Собственная стратегия:
   локальная очередь потока, приоритеты, учёт стоимости. В `Lab6/Task15` (пункт 15.4)
   реализован разделитель с локальным стеком и общей очередью.
5. **Разбиение по данным (data partitioning).** Хеш-разбиение: данные уже лежат по
   сегментам, параллелизм идёт по сегментам. Применяется в `Lab5/Task5` (ConcurrentDictionary)
   и в распределённых сценариях.
6. **Chunk + слияние.** Массив режется на блоки по числу ядер, блоки обрабатываются
   параллельно, затем сливаются. Применяется в `Lab6/Task16` (вариант 7, параллельная
   сортировка слиянием).

Выбор определяется характером нагрузки: равномерная — статическое, неравномерная —
динамическое или мелкие диапазоны.

### 5. Как выполняется агрегация результатов параллельных вычислений?

Четыре способа, от худшего к лучшему:

1. **Блокировка на каждый элемент** — `lock` внутри тела цикла. Корректно, но все
   потоки стоят в очереди: параллелизм пропадает. В `Lab6/Task12` этот вариант
   отработал за 716 мс против 22 мс у лучшего.
2. **`Interlocked` на каждый элемент** — дешевле `lock`, но точка конкуренции
   остаётся. В том же задании — 147 мс.
3. **Локальное состояние итерации (рекомендуется).** Перегрузка с `localInit`
   выдаёт каждому диапазону его собственный аккумулятор, `localFinally` сводит
   частные итоги. Блококировок в горячем цикле нет. 22 мс.
4. **Разделимость результата по индексу.** Каждый поток пишет в
   `results[threadIndex]`, свод делается после цикла проходом по массиву. Ноль
   синхронизации внутри цикла — самый быстрый вариант, применён в
   `Lab6/Task12` (пункт 12.2) и `Lab6/Task16` (вариант 1).

Вывод: агрегат должен быть **композиционным** (сумма, минимум, максимум) либо
записываться в ячейку по индексу. Общий счётчик с блокировкой — почти всегда
ошибка проектирования, а не необходимость.

### 6. Когда следует использовать параллельное программирование вместо последовательного?

**Параллелизировать стоит, когда выполняются все условия:**

1. Задача **вычислительно интенсивна** (занимает CPU), а не ждёт ввода-вывода.
2. Объём данных достаточен: работа на элемент заметно превышает накладные расходы
   на запуск потока. Порог на практике — единицы микросекунд на элемент.
3. Задача **разделяема**: части независимы и не пишут в общие данные.
4. Есть **выигрыш в объёме** относительно целевой машины.
5. Стоимость синхронизации меньше выигрыша от параллелизма.

**Не параллелизировать:**

* I/O-bound задачи — там хватает `async/await` (запрос 20 файлов через `Task.WhenAll`
  занимает 1500 мс вместо 3600 мс, и это не про потоки CPU);
* короткие задачи: 1000 задач в пуле против 1000 `Thread` дали разницу в пользу пула
  (`Lab5/Task2`), а на уровне одного цикла накладные расходы съедают всё ускорение;
* задачи с сильной зависимостью между элементами;
* когда важнее предсказуемость, а не скорость (один короткий цикл, где 22 мс против
  63 мс в `Lab6/Task12` — не тот выигрыш, который стоит сложности кода);
* задачи, упирающиеся в память или ввод-вывод, а не в CPU: тогда распараллеливание
  не поможет, а вредный код усложнит отладку.

Практический критерий: **сначала измерить последовательно, потом распараллелить,
затем снова измерить и оставить параллелизм только если выигрыш устойчив**.
Именно так построены все замеры в лабораторной работе.
