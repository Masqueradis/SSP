# Задание 2 — Исследование LOH (Large Object Heap)

**Проект:** `Lab4/Task2` · **Запуск:** `cd Lab4/Task2 && dotnet run`

## Что делает программа

Три части: определение порога LOH, мониторинг LOH на 100 объектах по 100 КБ,
демонстрация фрагментации и её устранения через `CompactOnce`.

## 2.1. Порог LOH

```
  small = new byte[80000]: поколение Gen0, размер 80000 байт
  large = new byte[90000]: поколение Gen2, размер 90000 байт
  упакованный int: поколение Gen0 (LOH не занимает)
  массив int[30000] (120 008 байт данных): поколение Gen2 -> LOH
```

Определение попадания в LOH — через поколение, потому что LOH является частью Gen2:

```csharp
Console.WriteLine($"large: Gen{GC.GetGeneration(large)}");  // Gen2
```

Важное различие: в LOH попадает **память данных массива**, а не объект-обёртка.
Упакованный `int` (24 байта) никогда не попадёт в LOH, а `int[30000]`
(120 008 байт данных) — попадёт.

### Точный порог найден перебором

```
  Первый размер ДАННЫХ, при котором массив попадает в LOH: 84976 байт
  Полный размер объекта при этом: 85000 байт (заголовок массива byte[] на x64 = 24 байта)
  Проверка: byte[84975] -> Gen0 -> обычная куча
  Проверка: byte[84976] -> Gen2 -> LOH
```

**Вывод:** порог 85 000 байт применяется к **полному размеру объекта**.
На x64 у массива заголовок 24 байта, поэтому 84976 + 24 = 85000 — ровно порог.
Длина данных `byte[]` = полный размер − 24.

## 2.2. Мониторинг LOH

Используется `GC.GetGCMemoryInfo()` с индексацией по поколениям:

```csharp
GCMemoryInfo info = GC.GetGCMemoryInfo();
ReadOnlySpan<GCGenerationInfo> generations = info.GenerationInfo;
// generations[0] = Gen0, [1] = Gen1, [2] = Gen2, [3] = LOH
```

> Тонкость API: в .NET 10 `GenerationInfo` — это `ReadOnlySpan<GCGenerationInfo>`,
> а не массив. Копировать его в `var` нельзя, нужно обращаться по индексу
> напрямую (как в коде выше). Это частая ошибка компиляции.

Четыре последовательных состояния:

| Шаг | Состояние | LOH | Фрагментация |
|-----|-----------|-----|--------------|
| 1 | до выделения | 0,00 МБ | 0,0 % |
| 2 | 100 × 100 КБ, `GC.Collect(2)` | 9,77 МБ | 0,0 % |
| 3 | ссылки отпущены, `GC.Collect(2)` | 9,77 МБ | **99,0 %** |
| 4 | `CompactOnce` + сборка | 0,10 МБ | **0,0 %** |

Ключевой момент для объяснения преподавателю: на шаге 2 `GC.Collect(2)` **не**
освобождает LOH, потому что массивы ещё достижимы из массива `keepAlive`.
Только после отпускания ссылок объекты становятся мусором.

## Разница между освобождением и уплотнением

Это главное различие, которое часто путают:

- **Освобождение (сборка мусора)** — освобождает *недостижимые* объекты.
  Работает при `GC.Collect(2)`, если ссылок не осталось.
- **Уплотнение (компактизация)** — перемещает *живые* объекты, закрывая промежутки.
  Ничего не освобождает, но убирает дыры в куче. Работает **только по явному запросу**.

Уплотнение LOH включается так:

```csharp
GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;
GC.Collect(2);
```

Флаг действует один раз: следующая полная сборка выполняет уплотнение и сбрасывает
режим в `Default`.

## Почему LOH не уплотняется автоматически

LOH не уплотняется **по умолчанию**, потому что это дорого: перемещение крупных
объектов копирует большой объём памяти, а на практике крупные объекты живут долго
(буферы, большие массивы, `StringBuilder`) и уплотнять их невыгодно. Автоматическое
уплотнение при каждой Gen2-сборке было бы непропорционально дорогим.

## Практические рекомендации

- Уплотнять **после** освобождения ссылок — иначе уплотнять нечего.
- Вызывать редко: это полная блокирующая сборка с паузой.
- Статические массивы-буферы в LOH — классическая утечка: они не собираются никогда.
- Для больших временных буферов использовать пул (`ArrayPool<T>`) — он переиспользует
  массивы и не создаёт давление на LOH.
