# Задание 1 — Исследование утечек памяти

**Проект:** `Lab4/Task1` · **Запуск:** `cd Lab4/Task1 && dotnet run`

## Что делает программа

Показывает два вида утечек памяти и доказывает их инструментами GC, а не
утверждениями. Каждая утечка подтверждается тремя независимыми способами:
счётчиками сборок, `GC.GetTotalMemory` и `WeakReference.IsAlive`.

### Часть 0. Статическое поле против экземплярного

Сначала показывается разница в семантике на простом примере: два экземпляра
класса делят один статический список, но имеют разные экземплярные списки.

```
Экземпляр 1 -> статический список: [111,222]
Экземпляр 2 -> статический список: [111,222]
Экземпляр 1 -> свой список:       [1]
Экземпляр 2 -> свой список:       [2]
Вывод: статический список ОДИН на все экземпляры, экземплярные списки разные.
```

### Часть 1.1. Статическая утечка

Создаётся 1000 объектов, у каждого `byte[10 * 1024]`. Половина кладётся
в статический список, половина — в экземплярный.

```
--- Старт (после полной сборки): 0.05 МБ ---
--- После GC.Collect() — прирост отн. старта: 19.61 МБ ---
  Элемент СТАТИЧЕСКОГО списка жив после полного GC: True
--- После Clear() и полной сборки: 0.04 МБ ---
  Элемент СТАТИЧЕСКОГО списка жив после Clear(): False
```

Почему 19,61 МБ, а не 9,77 МБ: удерживаются **оба** списка, каждый по
1000 × 10 КБ = 9,77 МБ.

### Часть 1.2. Событийная утечка

Создаётся источник со статическим событием, на него подписываются 100
подписчиков, каждый из которых удерживает кэш 100 КБ.

```
Удерживается кэшем подписчиков: 9.77 МБ
--- После событий и GC.Collect() — прирост отн. старта: 9.79 МБ ---
  Подписчик №1 жив после полному GC: True
  Подписчик №100 жив после полному GC: True
--- После отписки и полной сборки — прирост отн. старта: 0.01 МБ ---
  Подписчик №1 жив после отписки: False
  Подписчик №100 жив после отписки: False
```

## Причины утечек

**Статический список** — статическое поле является корнем GC, оно существует
всё время работы процесса, поэтому список и все его элементы остаются
достижимыми бесконечно. `GC.Collect()` не освобождает достижимые объекты.

**Событие** — `publisher.Event += subscriber.Handler` создаёт делегат, который
хранит ссылку на target (объект-подписчик) и помещается в поле издателя.
Получается двусторонняя ссылка `издатель → делегат → подписчик`. При статическом
источнике события подписчики удерживаются до конца процесса.

## Как доказать утечку правильно

`WeakReference` — главный инструмент доказательства. Он не мешает сборщику
(в отличие от обычной ссылки) и позволяет проверить, жив ли объект:

```csharp
var weak = new WeakReference(target);
target = null;
GC.Collect();
GC.WaitForPendingFinalizers();
GC.Collect();
Console.WriteLine(weak.IsAlive);   // True => объект удерживается кем-то ещё
```

**Важная тонкость:** `GC.KeepAlive(target)` после проверки означал бы, что
объект нужно удержать **до** строки с проверкой, а не после. Если написать
`GC.KeepAlive(target)` *после* вывода `IsAlive`, всё будет корректно; если
*до* — на время проверки объект ещё жив и результат будет ложноотрицательным.

Двойная сборка (`GC.Collect()` → `WaitForPendingFinalizers()` → `GC.Collect()`)
нужна потому, что объекты с финализаторами переживают первую сборку: сначала
финализатор запускается, и только во втором проходе память освобождается.

## Что должно быть на экране

| Проверка | Ожидание |
|----------|----------|
| Прирост памяти при статическом списке | ~19,6 МБ (два списка по 9,77 МБ) |
| `IsAlive` до `Clear()` | `True` |
| `IsAlive` после `Clear()` | `False` |
| Прирост памяти при событийной утечке | ~9,79 МБ |
| Прирост после отписки | ~0,01 МБ |

## Типичные ошибки

- **Проверять до конца метода, удерживая ссылку.** Если переменная с объектом
  ещё жива в области видимости, JIT может её сохранить, и `IsAlive` даст ложь.
- **Считать `Working Set` вместо `GC.GetTotalMemory`.** Working Set включает
  память, которую процесс не вернул ОС, и включает память CLR. Для утечек
  показательнее `GC.GetTotalMemory` и `Private Bytes`.
- **Забыть про финализаторы.** Один `GC.Collect()` может не освободить объект,
  у которого есть финализатор.
