# Задание 5 — Профилирование производительности

**Проект:** `Lab4/Task5` · **Запуск:** `cd Lab4/Task5 && dotnet run`

Три файла: `Profiler.cs` (инструмент), `Workloads.cs` (нагрузка), `Program.cs` (сценарии).

## Как устроен профилировщик

Собственный инструмент на `Stopwatch`, без внешних пакетов — как требует условие.

### Call Tree со стеком

```csharp
using (profiler.Enter("Main"))
{
    ProcessLogs();   // вложенные Enter создают дочерние узлы
}
```

`Enter` кладёт кадр в стек, `Dispose` снимает его. Счётчики времени ведутся
в `Dictionary<string, int>` по идентификатору потока (потокобезопасно).

### Own Time

```
Own Time = Total Time метода − сумма Total Time дочерних вызовов
```

Это время, потраченное **самим** методом, а не его детьми. Именно Own Time
показывает, что оптимизировать: если метод просто вызывает другой горячий метод,
его собственное время мало.

### Калибровка накладных расходов

```
Калибровка: одна операция Enter/Exit профилировщика стоит 0.171 мкс.
Эти накладные расходы входят в Own Time родительских узлов, поэтому
собственное время узлов с большим числом вызовов слегка завышено.
```

Инструментированный вызов не бесплатен. Узел, внутри которого миллион
`Enter`/`Exit`, будет показывать Own Time больше истинного на
`0,171 мкс × число вызовов`. Поэтому калибровка выводится явно, а не прячется.

### Трек аллокаций

`GC.GetAllocatedBytesForCurrentThread()` до и после метода даёт объём
аллокаций каждого узла. Это второй важный показатель: `Split` может быть
не самым медленным, но самым аллоцирующим.

## Методика замеров, принятая в работе

Одиночный прогон нельзя использовать для выводов — в первом измерении
доминируют JIT-компиляция и холодные кэши. Поэтому:

1. **Прогрев** — метод вызывается несколько раз «вхолостую» до измерения.
2. **Несколько раундов** — 5 повторов.
3. **Минимум** — берётся наилучший результат, он наименее зашумлён.
4. **Реалистичный размер данных** — пул 10 000 уникальных строк, а не 20
   повторов одной строки, иначе всё попадёт в кэш процессора.
5. **Изоляция** — замер только разбора даты не включает генерацию данных.

Первый вариант программы давал `0.00 мс` в таблице сравнения, потому что
`Root.TotalMilliseconds` читался до `Complete()`. Исправлено.

## Часть 3. Проверка рекомендации задания — главный результат работы

Условие предлагает заменить `DateTime.TryParse` на `DateTime.ParseExact` с
фиксированным форматом, утверждая, что это ускорит код. **Замер этого не подтверждает.**

```
### Изолированный замер разбора даты (200 000 итераций, пул 10 000 строк, 5 раундов, минимум)
  Формат 1: yyyy-MM-dd HH:mm:ss.fff (формат данных из лабораторной)
    DateTime.TryParse      :    46.16 мс (231 нс на разбор)
    DateTime.TryParseExact :    72.77 мс (364 нс на разбор)
    Отношение              :     0.63 x
  Формат 2: dd.MM.yyyy HH:mm:ss (европейский)
    DateTime.TryParse      :    40.89 мс (204 нс на разбор)
    DateTime.TryParseExact :    54.37 мс (272 нс на разбор)
    Отношение              :     0.75 x
```

`TryParseExact` **медленнее** в обоих форматах. Причина: движок разбора даты
в .NET 7+ сильно оптимизирован, а `TryParseExact` при каждом вызове дополнительно
разбирает пользовательскую строку формата токен за токеном.

Проверка отдельным независимым экспериментом (Release-сборка, 7 раундов,
пул 10 000 строк) дала тот же результат — `0.44 x`, `0.61 x`, `0.71 x` для трёх
форматов, включая ISO 8601 с разделителем `T`. Это подтверждает, что вывод
не является случайным шумом.

**Что остаётся от рекомендации:** результат идентичен
(`TryParse vs ParseExact: аномалий 2727 и 2727`), а ценность `ParseExact` —
в строгости: независимость от текущей `Culture` (нет неоднозначности
`01.02.2026`) и отказ от угадывания формата для мусорного ввода.

### Настоящее узкое место

```
### Изолированный замер Regex vs ручной разбор (5 раундов, минимум)
  Regex.Match            :    2.278 мс
  IndexOf + ручной разбор:    0.065 мс
  Ускорение              :     35.2 x
  Это и есть главный резерв оптимизации в данном коде.
```

Замена `Regex.Match(@"Code:\s*(\d+)")` на `IndexOf("Code: ")` + ручной разбор
цифр даёт кратное ускорение. Регулярное выражение — универсальный конечный
автомат с возвратами, решающий задачу «выделить число после известного префикса»
в тысячу раз сложнее необходимого.

## Часть 4. Профилирование собственного кода

Собственный код — анализатор частоты слов в логах: `Dictionary<string,int>`,
`Split`, фильтрация стоп-слов, отчёт топ-N.

```
Проанализировано записей: 10,000, токенов: 61,172, уникальных слов: 56
Время: 55.07 мс, аллокаций: 13.52 МБ
Топ-10 слов: after = 2077; Request = 2011; connection = 2001; exceeded = 1983; ...
```

```
### Топ-5 узлов собственного кода по Own Time
  OwnCode.Tokenize         20.80 мс   31.6% вызовов 10100
  OwnCode.CountWords       18.49 мс   28.1% вызовов 1
  OwnCode.BuildReport      12.87 мс   19.5% вызовов 1
  OwnCode.DictionaryLookup 12.06 мс   18.3% вызовов 55427
  OwnCode.String.Join       0.02 мс    0.0% вызовов 1
```

**Главное наблюдение:** `DictionaryLookup` вызывается 55 427 раз — больше всех,
но его собственное время **меньше**, чем у `Tokenize` (10 100 вызовов).
Частота вызовов ≠ стоимость вызова.

### Что пришлось исправить при отладке

Первая версия давала бессмысленный отчёт:

```
Топ-10 слов: 2026-09-27 = 10000; DEBUG = 2550; WARNING = 2477; 04.395 = 1017; ...
```

В «слова» попадали дата, уровни лога и октеты IP, потому что `Split` разделял
строку только по `' '`, `'|'`, `':'`. Исправлено:

- токен принимается, только если **все символы буквы** (`char.IsLetter`);
- добавлены стоп-слова уровней лога: `debug`, `warning`, `warn`, `error`,
  `info`, `fatal`, `critical`, `trace`;
- длина не менее 3 символов.

После этого 61 172 токена, 56 уникальных слов, топ — смысловые слова.
Это пример того, что **профилирование бесполезно, если нагрузка нерепрезентативна**:
замер красивых цифр по мусорным входным данным бесполезен.

## Ограничения инструмента

Инструмент не измеряет ввод-вывод, блокировки и работу планировщика —
для этого нужны `dotnet-counters` и `dotnet-trace`. Для поиска горячих путей
внутри вычислений (а это предмет лабораторной работы) его достаточно.
Это ограничение указано в выводе программы явно.
