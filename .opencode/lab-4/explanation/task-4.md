# Задание 4 — Поиск и исправление утечек

**Проект:** `Lab4/Task4` · **Запуск:** `cd Lab4/Task4 && dotnet run`

## Что делает программа

Берёт код `BuggyCode` из условия, находит в нём проблемы, а затем **доказывает**
каждую замером: создаёт 200 экземпляров, теряет на них ссылки и проверяет
выживание через `WeakReference`. Затем сравнивает с `FixedCode`.

## Исходный код из условия

```csharp
public class BuggyCode
{
    private static List<IDisposable> _cache = new List<IDisposable>();
    private static event EventHandler _globalEvent;
    private byte[] _data = new byte[1024 * 1024];

    public BuggyCode()
    {
        _globalEvent += OnEvent;
        _cache.Add(new MemoryStream(1024));
    }

    private void OnEvent(object sender, EventArgs e)
    {
        var temp = new byte[1024 * 100];
    }
}
```

## Найденные проблемы

### Проблема 1. Статическая коллекция `_cache` растёт бесконечно

**Причина:** поле `static` — корень GC, существующий всё время работы процесса.
Каждый `new BuggyCode()` добавляет в `_cache` ещё один `MemoryStream`.

**Последствие:** статический кэш не даёт сборщику освободить `MemoryStream`
и его внутренний буфер. Обратите внимание: сами экземпляры удерживаются
проблемой 2, а `_cache` удерживает потоки.

**Исправление:** ограничить размер кэша и освобождать элементы при вытеснении,
поле сделать `readonly`.

### Проблема 2. Статическое событие удерживает каждый экземпляр

**Причина:** `_globalEvent += OnEvent` сохраняет ссылку на метод экземпляра,
а значит, и на сам объект `BuggyCode`. Источник события статический и живёт вечно,
поэтому и подписчик вечен.

**Исправление:** отписываться в `Dispose`, не подписываться на статическое
событие вовсе, либо хранить подписки в `WeakReference`.

### Проблема 3. Отсутствие `IDisposable` — утечку нечем устранить

**Причина:** класс не реализует `IDisposable`, значит нельзя ни отписаться,
ни освободить `IDisposable`-ресурсы из `_cache`.

**Исправление:** реализовать `IDisposable`, вызывать через `using`,
`MemoryStream` из `_cache` освобождать при вытеснении.

### Проблема 4. `new byte[1024 * 100]` — это **НЕ** утечка

Важное разграничение, ради которого задание и формулирует «3-4 места».
`temp` — локальная переменная, её время жизни заканчивается вместе с вызовом
метода, поэтому GC освободит её сразу.

**Но** есть проблема производительности:

- при каждом событии выделяется 100 КБ мусора;
- 100 КБ > 85 000 байт, значит мусор попадает в **LOH**, а он не уплотняется;
- при частом событии это нагружает Gen2/LOH-сборку.

**Исправление:** переиспользовать один буфер-поле вместо выделения нового.

## Доказательство замером

```
ЗАМЕР 1 — BuggyCode: создаём 200 экземпляров, затем теряем ссылки
Старт: 0.05 МБ
После создания 200 экземпляров и полной сборки: 200.30 МБ
Прирост: 200.25 МБ
Экземпляров создано: 200, элементов в _cache: 200
Ссылок на объекты в коде больше нет, но все 200 объектов живы:
  WeakReference.IsAlive == true у 200 из 200 объектов
  => УТЕЧКА ПОДТВЕРЖДЕНА
```

200 × 1 МБ = ~200 МБ — совпадает с измеренным приростом 200,25 МБ.
Это ровно массивы `_data`, удерживаемые событием.

```
ЗАМЕР 2 — повторный эксперимент с удвоением
Старт: 200.29 МБ
После создания 200 экземпляров: 400.54 МБ (прирост 200.25 МБ)
Подписчиков на статическом событии: 200
Размер _cache продолжает расти с каждым new BuggyCode(): 200 элементов.
```

```
ЗАМЕР 3 — вызываем Dispose() для всех зарегистрированных экземпляров
После Dispose(): 200.30 МБ (прирост отн. старта 0.01 МБ)
  WeakReference.IsAlive == true у 0 из 200 объектов
  => УТЕЧКИ НЕТ: после Dispose все объекты собираются GC.
```

Рост **линейный** (200 → 400 МБ при добавлении ещё 200 экземпляров) — это
подтверждение именно утечки, а не разового замера.

## Что именно делает `FixedCode`

- поле `_registry` — `readonly`, снимок для обхода (защита от `InvalidOperationException`
  при изменении коллекции во время `foreach`);
- `Dispose()` **идемпотентен** — повторный вызов ничего не делает (поле `_disposed`);
- отписка `_globalEvent -= OnEvent` в `Dispose`;
- `MemoryStream` из `_cache` вызывается `Dispose()` при вытеснении и при очистке;
- буфер `OnEvent` — переиспользуемое поле, а не новая аллокация.

## Что должно быть на экране

| Проверка | Ожидание |
|----------|----------|
| Прирост памяти `BuggyCode` | ~200,25 МБ |
| Выжило объектов `BuggyCode` | `200 из 200` |
| Рост при повторном эксперименте | линейный (200 → 400 МБ) |
| Выжило объектов `FixedCode` | `0 из 200` |
| Прирост после `Dispose` | ~0,01 МБ |
| Повторный `Dispose` | безопасен, эффекта нет |
