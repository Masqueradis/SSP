# Testing Guide — Лабораторная работа 4

**Тема:** Утечки памяти (статические коллекции, события), Large Object Heap,
boxing/unboxing и профилирование производительности в C#

Пошаговая инструкция по запуску, демонстрации и сдаче преподавателю.

Выполнено на **.NET 10** (проверено: `dotnet --version` → 10.0.112).
Все проекты — в `Lab4/Task1` … `Lab4/Task5`, каждое задание — самостоятельный
консольный проект, который печатает отчёт с замерами.

> Примечание: если на машине преподавателя стоит только SDK 8.0, нужно либо
> установить .NET 10 SDK, либо в каждом `.csproj` заменить
> `<TargetFramework>net10.0</TargetFramework>` на `net8.0`.
> Код написан на API, доступных и в `net8.0` (кроме `GC.GetGCMemoryInfo()`,
> который тоже есть с .NET 5), поэтому смена TFM безопасна.
> Заявление `ReadOnlySpan<GCGenerationInfo>` требует C# 12+ (SDK 7.0+).

## 2. Задание 1 — Исследование утечек памяти

**Что показывает:** два вида утечек — статическая коллекция и событийная подписка.

**Ожидаемый вывод (ключевые строки):**

```
ЛАБОРАТОРНАЯ РАБОТА 4 — ЗАДАНИЕ 1: ИССЛЕДОВАНИЕ УТЕЧЕК ПАМЯТИ
Среда: 10.0.12  |  Рабочие процессоры: 8
```

Часть 1.1 — статический список:

```
--- Старт (после полной сборки): 0.05 МБ ---
### Создаём 1000 объектов по 10 КБ
В статическом списке: 1000 элементов, в экземплярном: 1000
--- После GC.Collect() — прирост отн. старта: 19.61 МБ ---
  Элемент СТАТИЧЕСКОГО списка жив после полного GC: True  <- статический корень удерживает объект
--- После Clear() и полной сборки: 0.04 МБ ---
  Элемент СТАТИЧЕСКОГО списка жив после Clear(): False <- объект собран, память освобождена
```

**Что говорить преподавателю:** прирост 19,61 МБ больше ожидаемых 9,77 МБ,
потому что удерживаются два списка одновременно. `GC.Collect()` не помогает —
значит объекты **достижимы**. После `Clear()` память освобождается полностью.

Часть 1.2 — событие:

```
### Подписываем 100 обработчиков; каждый подписчик удерживает кэш 100 КБ
Удерживается кэшем подписчиков: 9.77 МБ
--- После событий и GC.Collect() — прирост отн. старта: 9.79 МБ ---
  Подписчик №1 жив после полному GC: True  <- делегат события удерживает подписчика
--- После отписки и полной сборки — прирост отн. старта: 0.01 МБ ---
  Подписчик №1 жив после отписки: False <- собран
```

**Что говорить:** 9,79 МБ живут после полной сборки и исчезают после отписки —
это и есть удержание по цепочке `издатель → делегат → подписчик`.

**Что должно быть на экране для успешной сдачи:** переход `True` → `False`
для обоих случаев, счётчики сборок растут, `Private Bytes` увеличивается.

## 3. Задание 2 — Исследование LOH

**Что показывает:** порог LOH, мониторинг Large Object Heap, фрагментацию
и её устранение через `CompactOnce`.

**Ожидаемый вывод:**

```
ЛАБОРАТОРНАЯ РАБОТА 4 — ЗАДАНИЕ 2: ИССЛЕДОВАНИЕ LOH
Среда: 10.0.12  |  Порог LOH: 85 000 байт
```

```
  small = new byte[80000]: поколение Gen0, размер 80000 байт
  large = new byte[90000]: поколение Gen2, размер 90000 байт
  упакованный int: поколение Gen0 (LOH не занимает)
  массив int[30000] (120 008 байт данных): поколение Gen2 -> LOH

### Поиск порога перебором размеров массива
  Первый размер ДАННЫХ, при котором массив попадает в LOH: 84976 байт
  Полный размер объекта при этом: 85000 байт (заголовок массива byte[] на x64 = 24 байта)
  Проверка: byte[84975] -> Gen0 -> обычная куча
  Проверка: byte[84976] -> Gen2 -> LOH
```

**Что говорить:** порог относится к **полному** размеру объекта, поэтому
84976 + 24 = 85000. `Gen2` в выводе — признак попадания в LOH.

Мониторинг 100 объектов по 100 КБ:

```
### 2. После выделения + GC.Collect(2)
  LOH: размер после GC: 9.77 МБ, фрагментация: 0.00 МБ (0.0 %)
  => GC.Collect(2) НЕ освобождает LOH: объекты ещё достижимы из keepAlive.
### 3. После освобождения ссылок + GC.Collect(2)
  LOH: размер после GC: 9.77 МБ, фрагментация: 9.67 МБ (99.0 %)
  => Объекты стали недостижимы, и Gen2/LOH-сборка их освободила.
### 4. После GCSettings.LargeObjectHeapCompactionMode = CompactOnce
  LOH: размер после GC: 0.10 МБ, фрагментация: 0.00 МБ (0.0 %)
```

**Что говорить:** обратите внимание на разницу между **освобождением**
(сборка недостижимого) и **уплотнением** (перемещение живого). Сначала массивы
ещё достижимы из `keepAlive`, поэтому `GC.Collect(2)` их не тронул. После
освобождения ссылок они собираются, и остаётся фрагментация 99 %, которую
убирает только явный `CompactOnce`.

**Что должно быть на экране:** фрагментация `99.0 %` до уплотнения и `0.0 %` после.

## 4. Задание 3 — Оптимизация boxing/unboxing

**Что показывает:** стоимость упаковки `int` в `object` и как её убрать.

**Ожидаемый вывод:**

```
ЛАБОРАТОРНАЯ РАБОТА 4 — ЗАДАНИЕ 3: ОПТИМИЗАЦИЯ BOXING/UNBOXING
Среда: 10.0.12  |  Число элементов: 1,000,000
```

```
### С упаковкой: List<object>.Add(int) -> boxing на каждом вызове
  List<object> (упаковка)                            84.04 мс      38.90 МБ  сборок Gen0: 5
### Без упаковки: List<int>.Add(int) -> значение лежит в массиве
  List<int> (без упаковки)                            5.06 мс       8.00 МБ  сборок Gen0: 0
```

Оптимизация существующего кода:

```
  UnoptimizedCode.Add -> ArrayList                   63.26 мс      38.89 МБ  сборок Gen0: 3
  OptimizedCode.Add -> List<int>                      6.72 мс       8.00 МБ  сборок Gen0: 0
```

Скрытая упаковка при переборе:

```
  foreach по IEnumerable (объектная версия): аллокаций 24000384 байт, сумма 499999500000
  foreach напрямую по List<int>:            аллокаций 0 байт, сумма 499999500000
  Причина: IEnumerable — объектный интерфейс, поэтому перечислитель упаковывается
```

**Что говорить:** 1 000 000 упакованных `int` = 24 000 000 байт (по 24 байта
на объект), поэтому `List<object>` весит 38,89 МБ против 8,00 МБ у `List<int>` —
разница в 4,9 раза ровно соответствует объёму мусора от упаковки.

Отдельная важная демонстрация — ловушка, найденная при замерах:

```
ЛОВУШКА, НАЙДЕННАЯ ПРИ ЗАМЕРЕ: GC.KeepAlive УПАКОВЫВАЕТ int
  GC.KeepAlive имеет сигнатуру KeepAlive(object), поэтому вызов
  GC.KeepAlive(temp) с переменной типа int САМ создаёт объект 24 байта.
  Первая версия этого замера показала одинаковые 240 000 байт в обоих циклах.
```

**Что говорить:** это хороший пример того, что замер может врать из-за самого
измерителя. `GC.KeepAlive(object)` неявно упаковывает `int` — чтобы этого избежать,
нужно передавать заведомо объектную ссылку (например, результат в поле класса).

**Что должно быть на экране:** `38.90 МБ` против `8.00 МБ`, `24000384` против `0` байт.

## 5. Задание 4 — Поиск и исправление утечек

**Что показывает:** анализ `BuggyCode` из условия (4 проблемы) и рабочий `FixedCode`
с `IDisposable`, который реально освобождает память.

**Ожидаемый вывод:**

```
ЛАБОРАТОРНАЯ РАБОТА 4 — ЗАДАНИЕ 4: ПОИСК И ИСПРАВЛЕНИЕ УТЕЧЕК
АНАЛИЗ КОДА BuggyCode — 4 НАЙДЕННЫЕ ПРОБЛЕМЫ
```

Программа сначала печатает исходный код из условия, затем разбор каждой проблемы
с объяснением и исправлением, потом сравнительный замер:

```
  Удерживается объектов (BuggyCode) : 200 из 200
  Удерживается объектов (FixedCode) : 0 из 200
  Прирост памяти (BuggyCode)       : ~200.25 МБ
  Прирост памяти (FixedCode)       : ~0.00 МБ
```

**Что говорить:** `WeakReference.IsAlive` — надёжный признак утечки: если объект
жив после `GC.Collect()`, на него кто-то ещё ссылается. Событие отписано, кэш
очищен, `MemoryStream` вызван `Dispose` — и 200 объектов собираются.

**Что должно быть на экране:** `200/200` против `0/200` и возврат памяти к базовой линии.

Дерево вызовов с Own Time и подсветкой горячих узлов:

    │   │   ├── IsAnomaly.String.Split

Часть 3 — проверка рекомендации задания замером:

```
### Изолированный замер разбора даты (200 000 итераций, пул 10 000 строк, 5 раундов, минимум)
  Формат 1: yyyy-MM-dd HH:mm:ss.fff (формат данных из лабораторной)
    DateTime.TryParse      :    46.16 мс (231 нс на разбор)
    DateTime.TryParseExact :    72.77 мс (364 нс на разбор)
    Отношение              :     0.63 x
```

```
### Изолированный замер Regex vs ручной разбор (5 раундов, минимум)
  Regex.Match            :    2.278 мс
  IndexOf + ручной разбор:    0.065 мс
  Ускорение              :     35.2 x
  Это и есть главный резерв оптимизации в данном коде.
```

**Что говорить (важнейший момент защиты):** рекомендация задания заменить
`TryParse` на `ParseExact` **реализована**, но замер показал, что на .NET 10
она не ускоряет код — `TryParseExact` медленнее. Мы это не скрываем, а показываем.
Настоящее ускорение найдено в другом месте — замена `Regex` на `IndexOf` с
ручным разбором, кратный выигрыш. **Это и есть главный вывод лабораторной работы:
оптимизацию выбирают замером, а не на веру.**

## 7. Контрольные вопросы

Ответы на все пять вопросов условия — в файле `answers.md`
(в корне `.opencode/lab-4/`). Кратко:

1. Объекты в статическом списке не удаляются, потому что статическое поле — **корень GC**,
   объект остаётся достижимым, и GC не имеет права его собрать.
2. События вызывают утечки, потому что подписка создаёт **двустороннюю ссылку**
   `издатель → делегат → подписчик`; долгоживущий издатель удерживает всех подписчиков.
3. Объекты >85 КБ попадают в LOH, чтобы сборщик не тратил время на уплотнение крупных
   объектов; порог 85 000 байт применяется к **полному** размеру объекта.
4. LOH не компактизируется **по умолчанию** — уплотнение там дорогое; уплотнить его
   можно явно через `GCSettings.LargeObjectHeapCompactionMode = CompactOnce`.
5. Максимальный Own Time у `Regex.Match` (универсальный парсер ради одного числа),
   `String.Split` (аллокации), `DateTime.*Parse` (замер показал, что `ParseExact`
   не быстрее на .NET 10) и `DateTime.Now` в цикле (системный вызов в цикле).
