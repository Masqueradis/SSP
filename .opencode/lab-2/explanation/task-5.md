# Задание 5 — Исследование Large Object Heap (LOH)

**Файл:** `Lab2/Task5/Program.cs`
**Целевая платформа:** .NET 10.0 (SDK 10.0.401)

---

## Что изучаем в этом задании

Large Object Heap (LOH) — это отдельная область управляемой кучи .NET для объектов **> 85 000 байт** (~83 КБ). LOH отличается от обычной кучи (SOH) несколькими важными свойствами:

1. **Не уплотняется** — при сборке мусора объекты не перемещаются, поэтому фрагментация не закрывается.
2. **Собирается только при Gen2** — частичные сборки Gen0/Gen1 LOH не затрагивают.
3. **Сразу попадает в Gen2** — объекты > 85 КБ минуют Gen0/Gen1.

В этом задании мы экспериментально подтверждаем эти свойства и изучаем поведение LOH через `GC.GetGeneration()`.

## Полный код

```csharp
using System;
using System.Collections.Generic;

class Program
{
    static void Main()
    {
        Console.WriteLine("=== Задание 5. Исследование Large Object Heap (LOH) ===\n");

        RunLOHCreation();    // Часть 1: создание объектов в LOH
        RunLOHMonitoring();  // Часть 2: мониторинг разных размеров

        Console.WriteLine("\nНажмите любую клавишу для завершения...");
        try { Console.ReadKey(); } catch { }
    }

    static void RunLOHCreation()
    {
        Console.WriteLine("1. Создание объектов в LOH: 100 массивов по 100 КБ.\n");
        Console.WriteLine($"Память ДО выделения: {GC.GetTotalMemory(false) / (1024 * 1024)} MB");

        var holder = new List<byte[]>();
        for (int i = 0; i < 100; i++)
        {
            holder.Add(new byte[100000]); // 100 КБ > 85 КБ → LOH
        }

        Console.WriteLine($"Память ПОСЛЕ выделения: {GC.GetTotalMemory(false) / (1024 * 1024)} MB");

        GC.Collect();
        GC.WaitForPendingFinalizers();

        Console.WriteLine($"Память ПОСЛЕ GC.Collect(): {GC.GetTotalMemory(false) / (1024 * 1024)} MB");
        Console.WriteLine($"Поколение LOH-объекта (100 КБ): {GC.GetGeneration(holder[0])}");

        Console.WriteLine("\nСравнение размещения 90 КБ и 80 КБ:");
        var arr90 = new byte[90000]; // 90 КБ > 85 КБ → LOH
        var arr80 = new byte[80000]; // 80 КБ < 85 КБ → SOH
        Console.WriteLine($"  90 КБ (> 85 КБ) -> поколение {GC.GetGeneration(arr90)}, размещён в LOH");
        Console.WriteLine($"  80 КБ (< 85 КБ) -> поколение {GC.GetGeneration(arr80)}, размещён в SOH (Gen0)");
        Console.WriteLine("=> Объекты больше 85 КБ сразу попадают в LOH и не уплотняются GC.");
    }

    static void RunLOHMonitoring()
    {
        Console.WriteLine("\n2. Мониторинг LOH с помощью GC.GetGeneration().\n");

        int[] sizesKB = { 10, 50, 90, 200 };
        var objects = new List<byte[]>();

        foreach (int kb in sizesKB)
        {
            var data = new byte[kb * 1024];
            objects.Add(data);
            bool inLoh = kb * 1024 > 85000;
            Console.WriteLine($"размер {kb,3} КБ: поколение {GC.GetGeneration(data)}, в LOH: {inLoh}");
        }

        GC.Collect();
        GC.WaitForPendingFinalizers();
        Console.WriteLine("\nПосле GC.Collect():");
        for (int i = 0; i < sizesKB.Length; i++)
        {
            int kb = sizesKB[i];
            var data = objects[i];
            bool inLoh = kb * 1024 > 85000;
            Console.WriteLine($"размер {kb,3} КБ: поколение {GC.GetGeneration(data)}, в LOH: {inLoh}");
        }
        Console.WriteLine("\nВывод: объекты 10 и 50 КБ живут в SOH и перемещаются по поколениям,");
        Console.WriteLine("90 и 200 КБ сразу попадают в LOH (поколение 2) и переживают сборки.");
    }
}
```

**Память не изменилась!** LOH не уплотняется — объекты остаются на месте.

**Шаг 5:** Проверяем поколение.
```
Поколение LOH-объекта (100 КБ): 2
```
Объект сразу в Gen2 — минует Gen0/Gen1.

**Шаг 6:** Сравниваем 90 КБ и 80 КБ.
```
  90 КБ (> 85 КБ) -> поколение 2, размещён в LOH
  80 КБ (< 85 КБ) -> поколение 0, размещён в SOH (Gen0)

Порог 85 КБ подтверждён: 90 КБ → LOH, 80 КБ → SOH.

**Шаг 1:** Создаём объекты 10/50/90/200 КБ.
```
размер  10 КБ: поколение 0, в LOH: False
размер  50 КБ: поколение 0, в LOH: False
размер  90 КБ: поколение 2, в LOH: True
размер 200 КБ: поколение 2, в LOH: True
```

**Шаг 2:** Вызываем `GC.Collect()` и проверяем поколения.
```
После GC.Collect():
размер  10 КБ: поколение 1, в LOH: False   ← перемещён в Gen1
размер  50 КБ: поколение 1, в LOH: False   ← перемещён в Gen1
размер  90 КБ: поколение 2, в LOH: True    ← остался в Gen2
размер 200 КБ: поколение 2, в LOH: True    ← остался в Gen2

**Наблюдение:**
- Объекты 10/50 КБ (SOH) переместились из Gen0 в Gen1 — обычное поведение.

## Ключевые концепции

### Почему LOH не уплотняется

**Компактизация** — это перемещение объектов в памяти для устранения фрагментации. Для обычных объектов (SOH) это нормально: GC копирует живые объекты в начало сегмента, обновляет ссылки.

Но для больших объектов (> 85 КБ) компактизация **дорога**:
- Нужно скопировать 100 КБ+ данных.
- Обновить все ссылки на перемещённый объект.
- Расход памяти на буфер копирования.

Поэтому LOH **не уплотняется** по умолчанию. Это приводит к фрагментации.

### Фрагментация LOH

```
LOH-сегмент: [ObjA 100KB] [ free 50KB ] [ObjB 200KB] [ free 80KB ] [ObjC 100KB]
```

Если удалить `ObjB`, получим «дыру» 200 КБ. Но новый объект 250 КБ **не поместится** в эту дыру (нужен непрерывный блок), хотя свободного места 200 + 50 + 80 = 330 КБ. Это **внешняя фрагментация**.

### Когда LOH собирается

| Тип сборки | Затрагивает LOH? |
|-----------|-----------------|
| Gen0 (обычная) | Нет |
| Gen1 (промежуточная) | Нет |
| Gen2 (полная) | **Да** |
| `GC.Collect(n)` (принудительная) | Зависит от поколения |

**Вывод:** LOH собирается **только при полной сборке Gen2**. Это самая дорогая сборка.

### Порог 85 КБ

Порог **85 000 байт** — историческое значение, выбранное разработчиками .NET Framework. Причины:
- Средний размер «большого» объекта в typical приложениях.
- Баланс между частотой сборки и размером копирования.

В .NET 5+ можно настроить порог через `GCSettings.LargeObjectHeapCompactionMode`, но это **опасно** (может вызвать замедление из-за копирования больших объектов).

## Типичные ошибки

1. **Считать, что LOH «сам себя чистит»** — LOH не уплотняется и собирается только при Gen2. Если вы создали 1000 больших объектов и удалили 999, в LOH останется фрагментация.

2. **Использовать большие объекты как временные** — `byte[100KB]` в цикле без сохранения ссылок: объект попадает в LOH, ссылка теряется, но объект **не удаляется** до Gen2. Это «временно-постоянная» утечка.

3. **Игнорировать фрагментацию** — В высоконагруженных серверах LOH-фрагментация может привести к `OutOfMemoryException` при наличии достаточного общего объёма памяти.

4. **Не знать порог 85 КБ** — Если вы создаёте объекты по 84 КБ, они попадают в SOH и уплотняются. Если по 86 КБ — в LOH и фрагментируются. Разница в 2 КБ может критично повлиять на производительность.

---

## Практическое применение

- **Буферы:** Если нужны временные буферы > 85 КБ, лучше использовать пул объектов (`ArrayPool<T>`) вместо аллокаций в LOH.
- **Строки:** Длинные строки (> 85 КБ) попадают в LOH. Используйте `StringBuilder` для конкатенации.
- **Массивы:** Если массив > 85 КБ и используется повторно — пулруйте его, а не создавайте заново.
- **Настройка compaction:** В .NET 5+ можно вызвать `GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce` перед сборкой для разовой компактизации LOH.
