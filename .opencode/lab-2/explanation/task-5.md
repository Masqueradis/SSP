# Задание 5 — Исследование Large Object Heap (LOH)

**Файл:** `Lab2/Task5/Program.cs`
**Целевая платформа:** .NET 10.0 (SDK 10.0.401)

## Суть задания

1. Создать объекты в LOH (массивы 100 КБ ×100), измерить память до/после,
   после `GC.Collect()`, сравнить размещение 90 КБ и 80 КБ.
2. Написать метод мониторинга LOH через `GC.GetGeneration()` для объектов
   10/50/90/200 КБ.

## Часть 1. Создание объектов в LOH

```
Память ДО выделения: 0 MB
Память ПОСЛЕ выделения: 9 MB
Память ПОСЛЕ GC.Collect(): 9 MB      <- LOH не сократилась
Поколение LOH-объекта (100 КБ): 2

90 КБ (> 85 КБ) -> поколение 2 (LOH)
80 КБ (< 85 КБ) -> поколение 0 (SOH, Gen1)
```

## Часть 2. Мониторинг LOH

```
размер  10 КБ: поколение 0  (SOH)
размер  50 КБ: поколение 0  (SOH)
размер  90 КБ: поколение 2  (LOH)
размер 200 КБ: поколение 2  (LOH)
После GC.Collect(): 10/50 КБ переходят в Gen1, 90/200 КБ остаются в Gen2.
```

## Вопросы для исследования

- **Почему объекты > 85 КБ не собираются компактно?** Компактизация — это
  копирование памяти. Перемещать большие объекты дорого, поэтому LOH не
  уплотняется по умолчанию, а после сборки освобождённые сегменты остаются
  фрагментированными (объекты удаляются, дыры не закрываются).
- **Как фрагментация LOH влияет на производительность?** Память дробится,
  для нового большого объекта может не найтись непрерывного участка даже при
  свободном месте → преждевременные сборки LOH (Gen2, дорогие) или
  `OutOfMemoryException`.
- **Когда LOH собирается GC?** Только при полной сборке (Gen2). Частичные
  сборки Gen0/Gen1 LOH не затрагивают.

## Вывод

Порог 85 000 байт подтверждён экспериментально: массивы ≤ 85 КБ попадают в
обычную кучу и «молодеют», > 85 КБ — сразу в LOH/Gen2.
