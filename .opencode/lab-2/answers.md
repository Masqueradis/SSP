# Ответы на контрольные вопросы — Лабораторная работа №2

## Вопрос 1 (Понимание Generations)

**Почему объекты в .NET перемещаются между поколениями (Gen0 → Gen1 → Gen2) и какие последствия это имеет для производительности? Приведите пример, как долгоживущий объект может привести к утечке памяти.**

Перемещение основано на эмпирической гипотезе «большинство объектов живут недолго».
- Gen0 — свежие объекты, сборка частая и дешёвая (маленький объём сканирования).
- Gen1 — промежуточный буфер, объекты, пережившие одну сборку.
- Gen2 — долгоживущие, сборка самая редкая и дорогая (сканируется вся куча).

Чем старше поколение, тем реже оно проверяется и тем дороже сборка, когда она всё же происходит. Следствие для производительности: платить за старые объекты приходится редко, но за дорогую полную сборку — много.

**Пример утечки через долгоживущий объект:** статическое поле (или событие) держит ссылку на объект. Объект переживает сборки, доходит до Gen2 и, пока существует корневая ссылка, никогда не будет собран — память «застряла» до конца приложения.

## Вопрос 2 (Статические ссылки)

**В чём принципиальная разница между статической и экземплярной ссылкой с точки зрения сборки мусора? Почему статические коллекции часто становятся источником утечек, даже если в них хранятся небольшие объекты?**

- **Статическая ссылка** — корень GC, живёт всё время жизни домена приложения; объект, на который она указывает (и всё, что он держит), не собирается.
- **Экземплярная ссылка** — часть другого объекта; исчезает вместе с ним; как только объект-владелец становится недостижимым, цепочка ссылок собирается GC.

Статическая коллекция удерживает **все** добавленные элементы до завершения программы. Даже если каждый элемент мал, при частом добавлении (например, логирование или кэш) объём растёт без контроля — это «медленная» утечка: объекты не нужны, но недостижимыми не становятся.

## Вопрос 3 (LOH и фрагментация)

**Почему LOH не подвергается компактизации при сборке мусора и как это влияет на производительность? Опишите сценарий, когда фрагментация LOH может стать проблемой.**

- Порог 85 000 байт: большие объекты не уплотняются по умолчанию, т.к. компактизация = копирование памяти, а перемещать большие объекты дорого.
- Влияние на производительность: после сборки освобождённые сегменты остаются разрозненными. Свободная память «дырявая».
- Проблемный сценарий: приложение часто аллоцирует и освобождает большие массивы (например, батчи данных, изображения). Даже при достаточном суммарном свободном объёме может не найтись непрерывного участка → преждевременные дорогие сборки Gen2 или `OutOfMemoryException`.

## Вопрос 4 (Событийные утечки)

**Почему неподписанные события — частые утечки в C#? Каков механизм и как исправить? Приведите пример безопасной подписки.**

Механизм: событие — поле-делегат на стороне **издателя**. Делегат хранит ссылку на обработчик, т.е. на объект-подписчик. Пока подписка существует (даже если на подписчика больше нет ссылок), GC видит его достижимым через корень (издателя) и не собирает.

Исправление:
- отписка в `IDisposable.Dispose()` (`publisher.Event -= subscriber.Handler`);
- слабые делегаты/`WeakEventManager` — событие не держит подписчика сильно;
- `CancellationToken` / запрос отмены для подписок.

Пример безопасной подписки:
```csharp
public sealed class Subscriber : IDisposable
{
    private readonly Publisher _publisher;
    public Subscriber(Publisher p) { _publisher = p; p.Changed += OnChanged; }
    private void OnChanged(object? s, EventArgs e) { /* ... */ }
    public void Dispose() { _publisher.Changed -= OnChanged; GC.SuppressFinalize(this); }
}
```

## Вопрос 5 (Boxing и производительность)

**Что такое упаковка и почему она негативно влияет на производительность и память? Как оптимизировать код с ArrayList / List<object> для целых чисел?**

Упаковка — превращение значимого типа (`int`) в ссылочный (`object`): значение копируется в новый объект на управляемой куче. Распаковка — обратное явное приведение. Каждая упаковка — аллокация объекта, которую потом обязан очистить GC.

Оптимизация: заменить `ArrayList`/`List<object>` на **обобщённый `List<int>`**. Тогда значения хранятся прямо в массиве, упаковка/распаковка исчезают.

Эксперимент (Task6): 1 000 000 операций — `List<object>` ≈ 82 мс и ~31 МБ кучи против `List<int>` ≈ 5 мс и ~4 МБ. `ArrayList → List<int>`: добавление быстрее в ~9–11x, суммирование в ~2.5x. Итог: скорость выше в 2–4 раза и более, нагрузка на GC меньше.

## Вопросы из Задания 4 (событийная утечка)

**Почему объекты в обработчике события не удаляются?**
Обработчик (объект-подписчик) держится ссылкой из делегата, а делегат — из поля-события издателя. Пока издатель жив и подписка существует, цепочка ссылок не разрывается — GC не имеет права удалить подписчика.

**Что происходит с памятью после отписки?**
Ссылка «подписка» исчезает. Если на подписчике больше нет других ссылок, он становится мусором и удаляется при следующем `GC.Collect()`. В эксперименте: 100 подписок → 25 МБ, после отписки → 0 МБ.

## Вопросы из Задания 5 (LOH)

**Почему объекты > 85 КБ не собираются компактно?**
Дорого копировать большие блоки; отказ от компактизации экономит время сборки (но приводит к фрагментации).

**Как фрагментация LOH влияет на производительность?**
Память разбивается на маленькие свободные куски; для нового большого объекта может не найтись непрерывного участка → лишние полные сборки (Gen2) или OOM.

**Когда LOH собирается GC?**
Только при полной (Gen2) сборке; сборки Gen0/Gen1 LOH не затрагивают.

## Вопросы из Задания 7 (BuggyCode)

Все 4 утечки в `BuggyCode` относятся к корневым ссылкам:

1. `static List<IDisposable> _cache` — никогда не очищается → рост и удержание `MemoryStream`.
2. `static event _globalEvent` — подписка `OnEvent()` в конструкторе без отписки → экземпляр всегда достижим.
3. `new MemoryStream(1024)` без `Dispose()` — утечка неуправляемых ресурсов даже после удаления ссылки.
4. `SubscribeAll()` — создаёт объекты, которые «никто не хранит», но их удерживают статика-событие и кэш.

Исправления: `Dispose()` (отписка + флаг `_disposed`), `Dispose()` элементов кэша и его очистка, принудительный `GC.Collect()` после очистки. Демонстрация: утечка 100 МБ не освобождается, исправленная версия освобождает 99 МБ.
