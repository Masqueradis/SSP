## Вопрос 1. Что такое рефлексия и для чего она используется в C#?

**Рефлексия (reflection, от англ. «отражение»)** — механизм .NET, который
позволяет программе **во время выполнения** получать *метаданные* о своих или
внешних типах и манипулировать ими: инспектировать классы, искать члены,
создавать объекты и вызывать методы без знания о типе на этапе компиляции.

Центральный объект — экземпляр класса `Type` (метаданные одного типа) и его
члены `MethodInfo`, `FieldInfo`, `PropertyInfo`, `ConstructorInfo`, `ParameterInfo`.
Всё это хранится в **сборке** (assembly): таблица типов, методов, полей и строк
IL-кода всегда доступна для чтения в рантайме — отсюда и «отражение».

### Основные сценарии использования

| Сценарий | Пример |
|----------|--------|
| Инспекция типов | дескомпилятор, отладчик, профилировщик, документация |
| **Позднее связывание** | загрузка типа по имени-строке, `Activator.CreateInstance` |
| **Плагины и надстройки** | приложение ищет DLL и загружает типы по интерфейсу |
| Работа с приватными членами | unit-тесты, попадание в скрытые поля/методы |
| Сериализация / ORM | Json.NET, EF Core, Dapper читают поля и свойства |
| DI-контейнеры | поиск типов, авто-регистрация сервисов |
| Атрибуты | `GetCustomAttribute<T>()` для аннотаций (E.g. маркер `[Plugin]`) |
| Инструменты | «фабрики» объектов по строковым именам, кастомные фреймворки |

### Пример «отражения»

```csharp
Type t = Type.GetType("DynamicCalculator")!;          // тип по строке
object obj = Activator.CreateInstance(t)!;            // объект без new
MethodInfo m = t.GetMethod("Add", new[] { typeof(int), typeof(int) })!;
object r = m.Invoke(obj, new object[] { 10, 20 });    // вызов по имени
Console.WriteLine(r);                                  // 30
```

> **Вывод:** рефлексия — это «API метаданных» платформы .NET, благодаря которой
> программа умеет работать с типами, которые она не видела на этапе компиляции.

## Вопрос 2. Какие пространства имён и классы необходимы для работы с рефлексией?

### Пространства имён

| Пространство | Что содержит |
|--------------|--------------|
| `System` | `Type`, `Attribute` (базовые типы) |
| `System.Reflection` | `MethodInfo`, `FieldInfo`, `PropertyInfo`, `ConstructorInfo`, `ParameterInfo`, `BindingFlags`, `Assembly` |
| `System.Reflection.Emit` | динамическая генерация IL (`DynamicMethod`, `ILGenerator`, `AssemblyBuilder`) |
| `System.Runtime.Loader` | изолированная загрузка сборок (`AssemblyLoadContext`) |

### Ключевые классы

- **`Type`** — «паспорт» типа: имя, пространство имён, базовый тип, интерфейсы,
  методы поиска членов (`GetMethods`, `GetField`, `GetProperty`, `GetConstructor`,
  `GetCustomAttributes`).
- **`MethodInfo`** / **`FieldInfo`** / **`PropertyInfo`** / **`ConstructorInfo`** —
  описания отдельных членов + операции: `Invoke`, `GetValue/SetValue`,
  `GetValue/SetValue`, `Invoke` соответственно.
- **`ParameterInfo`** — типы и имена параметров (`m.GetParameters()`).
- **`BindingFlags`** — флаги поиска (видимость, Instance/Static, etc.).
- **`Assembly`** — единица метаданных: загрузка файла (`LoadFrom`),
  типы (`GetTypes`, `GetType`), атрибуты сборки.
- **`Activator`** — создание экземпляров (`CreateInstance`).
- **`CustomAttributeData`** / **`Attribute`** — чтение атрибутов.

### Пример типового набора using

```csharp
using System.Reflection;   // MethodInfo, FieldInfo, BindingFlags, Assembly
using System;              // Type, Activator, Type.GetType
```

## Вопрос 3. В чём разница между GetType() и typeof()?

| Сравнение | `typeof(T)` | `obj.GetType()` | `Type.GetType(string)` |
|-----------|-------------|-----------------|------------------------|
| Контекст | статический (compile-time) | динамический (runtime) | динамический (по имени) |
| Что берёт | тип из набора известных | **фактический** тип объекта | тип по полному имени строкой |
| Требует экземпляр | нет | да (`obj`) | нет |
| Проверка компилятором | да | да (метод есть у всех) | нет (строка может не существовать) |
| Когда важен | когда тип известен с самого начала | при полиморфизме / `object` | когда тип неизвестен вовсе (позднее связывание) |

### Почему важно

```csharp
object o = new CalculatorPlugin();
o.GetType();                  // → CalculatorPlugin (реальный тип!)
typeof(object);               // → System.Object
typeof(IPlugin);              // → Task7.Plugins.IPlugin (интерфейс)
```

При полиморфизме `obj.GetType()` вернёт **фактический** runtime-тип, а не тип
переменной. Именно поэтому в Задании 3 для проверки созданного объекта писали
`calculator.GetType().Name` — тот же приём используется в плагинах для
получения конкретного типа после `Activator.CreateInstance`.

> **Итог:** `typeof` — «тип известен заранее», `GetType()` — «спроси у экземпляра»,
> `Type.GetType(строка)` — «найди по имени». Все три дают объект `Type`, но
> «съём» его происходит по-разному.

## Вопрос 4. Как получить доступ к приватным членам класса через рефлексию?

Приватные члены вносятся в метаданные сборки всегда — вопрос лишь в том, как их
найти и как с ними работать. План:

### Шаг 1. Получить `Type`
```csharp
Type t = typeof(MyClass);        // или obj.GetType(), или Type.GetType("MyClass")
```

### Шаг 2. Указать флаги видимости
```csharp
const BindingFlags NB = BindingFlags.NonPublic | BindingFlags.Instance;
const BindingFlags NB_STATIC = BindingFlags.NonPublic | BindingFlags.Static;
```

### Шаг 3. Найти член
```csharp
FieldInfo  secret  = t.GetField("_secret", NB);
MethodInfo compute = t.GetMethod("Compute", NB);
PropertyInfo p     = t.GetProperty("Secret");   // свойства находятся обычным путём
```

### Шаг 4. Работать
```csharp
// поле:
int v = (int)secret.GetValue(obj)!;
secret.SetValue(obj, 777);

// метод (object[] параметров, null для статических):
object result = compute.Invoke(obj, new object[] { 42 })!;

// свойство:
p.SetValue(obj, "новое значение");   p.GetValue(obj);
```

### Частые ловушки

- **Забыли `NonPublic`** → метод/поле «не найдены» (null), хотя они существуют.
- **Static vs Instance** — разные флаги: `NonPublic | Static` для статических.
- **Приватный сеттер** — `GetProperty + GetSetMethod(true)` или
  `GetMethod("set_X", NonPublic | Instance)`.
- **Только собственные члены** — `DeclaredOnly`, чтобы не тянуть базовый тип.

> Все эти приёмы непосредственно реализованы в Заданиях 5 (поле) и 6 (методы),
> а с приватным сеттером мы столкнулись в Задании 2 (`private set_Category`).

## Вопрос 5. Какие ограничения и риски связаны с использованием рефлексии?

### 1. Производительность
- `MethodInfo.Invoke` упаковывает/распаковывает параметры (boxing), ищет метод по
  имени каждый раз — реальные вызовы в разы (иногда десятки раз) медленнее
  прямых.
- **Способы снизить потери:**
  - кэшировать `MethodInfo`/`FieldInfo` (поиск один раз);
  - использовать `Delegate.CreateDelegate` (Задание 6, способ 2);
  - строить `Expression` и компилировать дерево один раз (Задание 6, способ 3);
  - использовать `MethodInfo` для многократных вызовов в цикле.

### 2. Безопасность
- Рефлексия **обходит инкапсуляцию**: приватные поля/методы доступны любому коду
  с полным доверием (full-trust).
- Под управлением частичного доверия (partial trust, iOS, UWP/AOT) часть API будет
  недоступна или бросит `SecurityException`.

### 3. Надёжность
- Имена обращаются **строками**: `GetMethod("HiddenAdd")` — опечатка не будет
  замечена компилятором; ошибка проявится только в рантайме (`null` или
  `MissingMethodException`).
- `TargetInvocationException` — если вызываемый метод бросает исключение, рефлексия
  оборачивает его в эту обёртку (искать `InnerException`).
- AOT-платформы могут «вырезать» метаданные (trimmer) → рефлексия перестанет видеть
  то, что понадобится.

### 4. Поддерживаемость
- Рефакторинг и переименования ломают рефлексивный код молча (рантайм-ошибки
  вместо compile-ошибок).
- Код сложнее читать, сложнее отлаживать, сложнее покрывать тестами.

### 5. Побочные эффекты
- «Лишние» опубликованные методы/поля усложняют поиск членов (вспомним 19 методов
  в Задании 2 вместо «наших» 2–3).
- Изменение состояния «в обход» ломает инварианты класса (см. Задание 5:
  после `SetValue` на `_multiplier` логика `Compute` меняется).

> **Вывод:** рефлексия — инструмент «на потом»: использовать точечно, кэшировать
> найденное, ставить проверки и try/catch, документировать имена.

## Вопрос 6. Что такое BindingFlags и для чего они используются?

`BindingFlags` — перечисление (`[Flags]`), управляющее **правилами поиска**
члена/типа в рефлексии. Комбинации флагов через `|` задают, **кто** именно
подпадает под поиск.

### Основные флаги

| Флаг | Действие |
|------|----------|
| `Public` | включать только публичные члены |
| `NonPublic` | включать private, protected, internal |
| `Instance` | экземплярные члены |
| `Static` | статические члены |
| `FlattenHierarchy` | добавить статические члены базовых классов |
| `DeclaredOnly` | только члены, объявленные в самом типе (без наследования) |
| `IgnoreCase` | поиск без учёта регистра |
| `GetField`/`GetMethod`/... | вспомогательные комбинации для поиска (см. ниже) |
| `InvokeMethod` | сигнал для вызова метода через `Invoke` |
| `SetField`/`SetProperty` | работа со значением поля/свойства |

### Правила-«закономерности»

1. **По умолчанию** поиск работает только с `Public | Instance`.
2. **Без `NonPublic`** приватные члены не находятся (проверено в Заданиях 2, 5).
3. **Для статических** обязателен `Static`.
4. **Недостаточно флага, если нет доступа**: `GetField`/`GetMethod` с `Public`
   не видят protected-члены, пока не добавить `NonPublic`.

### Примеры из лабораторной

```csharp
// Task2 — полный вид обычного типа:
type.GetMethods(BindingFlags.Public | BindingFlags.NonPublic |
                BindingFlags.Instance | BindingFlags.Static);

// Task5 — приватное поле:
type.GetField("_secret", BindingFlags.NonPublic | BindingFlags.Instance);

// Task6 — приватный статический метод:
type.GetMethod("Triple", BindingFlags.NonPublic | BindingFlags.Static);
```

### Комбинированные флаги (для полноты)

`BindingFlags.FlattenHierarchy` — нужен, чтобы увидеть статический член базового
класса (обычное «без» него статические члены базового типа в выдаче
отсутствуют).

## Вопрос 7. Как динамически создать экземпляр класса через рефлексию?

### Способ 1. `Activator.CreateInstance` без параметров

```csharp
Type t = Type.GetType("DynamicCalculator")!;
object obj = Activator.CreateInstance(t)!;         // конструктор по умолчанию
```

### Способ 2. `Activator.CreateInstance` с параметрами

```csharp
object obj = Activator.CreateInstance(calcType, new object[] { 42 })!;
```

`new object[]{ 42 }` — массив аргументов конструктора; CLR выберет конструктор
по типу параметров.

### Способ 3. Явный `ConstructorInfo`

```csharp
ConstructorInfo ctor = calcType.GetConstructor(new[] { typeof(int) })!;
object obj = ctor.Invoke(new object[] { 100 });
```

`GetConstructor(Type[])` — «точечный» поиск по типам параметров, `Invoke` —
создание экземпляра.

### Способ 4. Обобщённая форма (для известного типа)

```csharp
var calc = Activator.CreateInstance<DynamicCalculator>();
```

— но это уже не «позднее» связывание, а удобство API.

### Что дальше делают с объектом

```csharp
// свойства:
PropertyInfo label = t.GetProperty("Label")!;
label.SetValue(obj, "CalcFromReflection");          // запись
Console.WriteLine(label.GetValue(obj));             // чтение (через get_Label)

// методы:
MethodInfo add = t.GetMethod("Add", new[] { typeof(int), typeof(int) })!;
int r = (int)add.Invoke(obj, new object[] { 10, 20 })!;
```

> Все четыре способа и все операции показаны в Задании 3.

## Вопрос 8. В чём отличие позднего связывания от раннего?

### Раннее связывание (early binding)

```csharp
var calc = new DynamicCalculator();      // тип известен компилятору
int r = calc.Add(10, 20);                // вызов проверен компилятором
```

- тип, сигнатура и целевой вызов известны **на этапе компиляции**;
- компилятор проверяет всё, JIT генерирует прямой/виртуальный вызов:
  **быстро, надёжно, безопасно**.

### Позднее связывание (late binding)

```csharp
Type t = Type.GetType("DynamicCalculator")!;
object calc = Activator.CreateInstance(t)!;
MethodInfo m = t.GetMethod("Add", new[] { typeof(int), typeof(int) })!;
int r = (int)m.Invoke(calc, new object[] { 10, 20 })!;
```

- тип, метод и способ вызова определяются **в рантайме**;
- имя типа и имя метода — обычные строки (ошибки не видны компилятору);
- `Invoke` работает через упаковку/распаковку — медленнее;
- зато **программа не знает заранее**, какие типы существуют → это единственный
  способ реализовать плагины, скрипты, конфигурируемые системы.

### Когда что выбирать

| Критерий | Раннее | Позднее |
|----------|--------|---------|
| Тип изборен заранее | ✅ | ❌ |
| Скорость | высокая | низкая/средняя |
| Компиляторные проверки | есть | нет |
| Расширяемость | ограничена | максимальная |
| Использование | 99% кода | рефлексия, `dynamic`, плагины |

В .NET динамическое поведение можно получить и через ключевое слово `dynamic`
(компилятор генерирует вызовы через железный механизм DLR), но рефлексия даёт
полный контроль над процессом.

## Вопрос 9. Какие недостатки есть у рефлексии?

1. **Низкая производительность вызовов.** Упаковка/распаковка параметров, поиск
   по именам, невозможность инлайна JIT. → Смягчается кэшированием
   `MemberInfo`, делегатами и `Expression.Compile()` (Задание 6, способы 2–3).

2. **Нет проверок компилятора.** Опечатки в именах → рантайм-ошибки
   (`null`, `MissingMethodException`, `TargetInvocationException`). → try/catch
   и тщательные проверки.

3. **Сложнее код.** Чтение/отладка рефлексивного кода тяжелее чистого вызова,
   появляется множество обёрток, упаковок, кастов.

4. **Риски безопасности.** Обход инкапсуляции (приватные поля → `SetValue`),
   доступ на частичном доверии ограничен. «Пробить» модификаторы `private`
   можно всегда при полном доверии — значит, защита должна строиться другими
   средствами.

5. **Побочные эффекты.** Изменение `_multiplier`/`_secret` в обход инвариантов
   (Задание 5) портит логику `Compute` — состояние класса становится
   несогласованным.

6. **Проблемы рефакторинга.** Переименование члена молча ломает рефлексивный код.

7. **AOT и trimming.** На iOS/UWP/WebAssembly и в trimmed-сборках часть
   метаданных может отсутствовать → рефлексия «не видит» того, что сохранила.

8. **Порог сложности.** Верифицируемый IL и динамические методы
   (`Reflection.Emit`, `DynamicMethod`) нетипичны и плохо документируются.

> **Резюме:** рефлексия — мощный, но дорогой инструмент. Держите её подальше
> от «горячих путей» кода: находите один раз, кэшируйте, конвертируйте в
> делегаты, оборачивайте ошибки, и обязательно документируйте имена.
